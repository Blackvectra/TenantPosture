# NRG-Assessment Tool — Claude Code Project Context

**Author:** NRG Technology Services — nrgtechservices.com
**GitHub:** https://github.com/Blackvectra/NRG-Assessment-Tool
**Version:** 4.13.0
**Language:** PowerShell 7.0+
**Purpose:** Read-only Microsoft 365 security assessment framework for MSP multi-tenant environments.

## What This Tool Does

NRG-Assessment runs agentlessly against any Microsoft 365 tenant, collects security configuration data via Microsoft Graph and Exchange Online PowerShell, evaluates 204 controls against a license-aware baseline, and produces an interactive HTML report with executive summary, compliance matrix, attack scenario analysis, and NRG services pitch. It is a read-only assessment — it never modifies tenant configuration.

There are four entry points. `Invoke-NRGAssessment.ps1` runs against a single tenant interactively. `Invoke-NRGBatchAssessment.ps1` runs against all clients defined in `Config/clients.json` sequentially using GDAP delegated access, producing per-client reports and a batch summary. `Invoke-NRGSignInTriage.ps1` (v4.12.0) runs admin-scope sign-in IoC triage to rank likely-compromised users. `Invoke-NRGEmailAssessment.ps1` (v4.12.0) runs a per-user mailbox incident-response deep-dive.

The v4.12.0 Email-IR mode lives in the top-level `Email-IR/` subtree (`Lib/`, `Collectors/`, `Evaluators/`, `Publishers/`, `Testing/`), auto-loaded by the psm1 `$loadOrder`. Its evaluators use `EMAIL-*` and `SIGNIN-*` control IDs and are not in `Config/controls.json` — they are heuristic IoC checks, not baseline controls.

## Project Structure

`NRG-Assessment-Tool/` contains `Invoke-NRGAssessment.ps1` (single-tenant entry point), `Invoke-NRGBatchAssessment.ps1` (multi-tenant batch entry point), `Invoke-NRGBatchSignInTriage.ps1` (morning sweep across all GDAP clients), `NRG-Assessment.psm1` (module loader that dot-sources all subdirectories recursively), and `NRG-Assessment.psd1` (module manifest).

`Evaluators/` contains one file per workload, each function evaluating one control: `Test-NRGControl-AAD.ps1` (41 functions), `Test-NRGControlDefender.ps1` (18 functions), `Test-NRGControlTeams.ps1` (17 functions), `Test-NRGControlPurview.ps1` (15 functions), `Test-NRGControlSharePoint.ps1` (13 functions), `Test-NRGControlIntune.ps1` (13 functions), `Test-NRGControlCopilot.ps1` (5 functions), `Test-NRGControlPowerPlatform.ps1` (4 functions).

## Control Architecture

204 total controls across 9 workloads: Azure AD / Entra ID (AAD, 49), Exchange Online (EXO, 35), Defender for Office 365 (DEF, 24), Microsoft Teams (TMS, 22), SharePoint Online (SPO, 18), Purview / Compliance (PVW, 18), Microsoft Intune (INT, 17), Power Platform (PPL, 11), Email Auth DNS (DNS, 10). Severity breakdown: 13 Critical, 97 High, 67 Medium, 27 Low.

License-aware scoring is encoded per control via the `LicenseRequirement` string field in `controls.json` (e.g. "M365 Business Premium or Entra ID P1", "Defender for Office 365 P1", "E5 Compliance"). There are no separate per-tier baseline JSON files — the requirement lives on each control row.

**NIST SP 800-53 Rev 5 rollup.** All 204 controls carry a `References.NIST` citation, spanning 12 of the 20 800-53 families. `Lib/Get-NRGNISTFamilyCoverage.ps1` rolls findings up by control family (AC, AU, IA, SC, SI, …) and by individual 800-53 control, using the same score formula and denominator rules as `Get-NRGCoverageScore`. It parses the `NIST:` prefix off the flattened `FrameworkIds` string — never the bare identifier shape, which would also match CMMC's `IA.L2-3.5.3`. A finding citing controls in two families is counted in each, so family rows deliberately do not sum to the assessment total; every surface that renders them says so. The rollup appears in the HTML report (`id="nist-families"`), the Markdown summary, and a dedicated `NIST Families` sheet in the XLSX matrix. `NRG.NISTFamily.Tests.ps1` pins both the parsing and the controls.json invariant that every control carries a parseable NIST citation — a control missing one vanishes from the family view, shrinking that family's denominator and inflating its coverage.

**Report framework selection.** `Invoke-NRGAssessment.ps1 -Framework <NIST|CIS|SCuBA|CMMC|All>` decides which framework cards the HTML report shows. **NRG defaults to `NIST`; NLS defaults to `All`** — the single deliberate behavioral difference between the twins, pinned in each repo by `NRG.FrameworkDefault.Tests.ps1` because a careless mirror would silently flip it and the failure would be invisible (the report still renders and still scores correctly). The PUBLISHER default stays `@('CIS','SCuBA','NIST','CMMC')` in both; only the entry point differs, so direct callers and the other twin are unaffected. Narrowing is presentation only: `Publish-NRGAssessmentHTML` scores all four regardless of `-Frameworks`, controls.json keeps every citation, and a test asserts no framework score moves when the report narrows. The `.fw-grid` column count is interpolated from the displayed set — hardcoding 4 renders a single card at quarter width. `Publish-NRGNISTMatrix` also emits a **NIST-only HTML report** (alongside Markdown and XLSX) that mentions no other framework anywhere on the page; a test greps for CIS/SCuBA/CMMC/ISO/SOC/HIPAA/PCI/MITRE and fails on any leak.

**Standalone NIST matrix.** `Publish-NRGNISTMatrix.ps1` emits a single-framework 800-53 Rev 5 deliverable (Markdown always, XLSX via openpyxl) behind the `-NISTMatrix` switch on `Invoke-NRGAssessment.ps1`; `-AllFiles` implies it. Six sheets: Summary, Control Matrix (one row per 800-53 control x tool control), By Control, By Family, Physical & Device, Not Assessed. Official Rev 5 titles come from `Config/nist-800-53-catalog.json` via `Lib/Get-NRGNISTControlCatalog.ps1` — note the Rev 4 -> Rev 5 renames the tool cites (AC-11 Device Lock, AT-2 Literacy Training and Awareness, AU-2 Event Logging, AU-4 Audit Log Storage Capacity, AC-6(9) Log Use of Privileged Functions, AC-16 Security and Privacy Attributes); `NRG.NISTMatrix.Tests.ps1` pins them by name. **The matrix is strictly additive** — `Publish-NRGComplianceMatrix` keeps all ten frameworks and no existing output changes; a test asserts publishing it does not move the CIS/SCuBA/CMMC scores. Every rollup table carries an Error column so Met + Partial + Gap + Error + N/A sums to Assessed; without it a reader who adds a row up comes short and has no way to tell whether the missing rows were passes or failures.

**NIST physical / media / device controls.** `Config/nist-physical.json` defines 31 800-53 controls covering endpoint posture, media, maintenance, personnel, and physical/environmental protection, each with the device aspect it covers and two or more implementation options. `Lib/Get-NRGNISTPhysicalPosture.ps1` joins it against findings and renders in the HTML report (`id="nist-physical"`) and the Markdown summary. Each item declares a `Scope`: `Tenant` (10, fully evidenced by scored controls), `Hybrid` (7, partly evidenced, remainder off-tenant), or `Attested` (14, not observable from Microsoft 365 at all). **Nothing in this section is scored** — Tenant/Hybrid rows reflect findings already scored under their own control IDs, and `Attested` rows always report `Attestation required`, never a compliance state. That is the "advisory controls never claim compliance" rule applied to a whole section: the section exists so a reader cannot infer from a clean NIST family table that the physical families were assessed and passed. `NRG.NISTPhysical.Tests.ps1` enforces the scope contracts (Tenant must cite evidence controls; Hybrid must cite both halves; Attested must name the off-tenant evidence and cite none), verifies every `EvidenceControls` ID exists in `controls.json`, and feeds the posture a findings set that satisfies every control in the tool to prove the attested rows still refuse to claim anything.

**Device guide (no scanning).** `Publishers/Publish-NRGDeviceGuide.ps1` renders `Config/nist-physical.json` into a printable device/endpoint guide — 31 controls, 98 implementation options, Markdown plus self-contained HTML with print styling and no external assets. `New-NRGDeviceGuide.ps1` is its standalone entry point and **connects to nothing**: no sign-in, no Graph, no EXO, no endpoint access, so the guide is usable before a tenant is attached. `-ResultsPath` optionally annotates it with a prior run's verdicts. Two invariants are statically enforced by `NRG.DeviceGuide.Tests.ps1`: neither file may reference `Invoke-NRGGraphRequest` / `Connect-MgGraph` / `Invoke-RestMethod` / `Get-NRGRawData` etc., and supplying findings must not change the rendered options (a test diffs them with and without). Note `@($null).Count` is 1, not 0 — counting an omitted `-Findings` that way made the guide print "Assessment result: Not assessed" for controls nothing had assessed; strip nulls before counting.

**Device build standard.** `Config/device-baseline.json` holds 27 lifecycle requirements (procure / provision / harden / in-service / offboard), 23 mandatory, each with Why, How, `Nist` citations and `VerifiedBy` tool-control references. `Publishers/Publish-NRGDeviceBaseline.ps1` renders it as a printable checklist plus detail; `New-NRGDeviceGuide.ps1` emits it alongside the control reference as `<base>-baseline.md`/`.html`. Same no-network contract as the guide, statically enforced. `NRG.DeviceBaseline.Tests.ps1` verifies every `VerifiedBy` exists in controls.json and every `Nist` entry resolves in the 800-53 catalog — both rot silently as the tool changes — and pins the mandatory set (DB-2.1 enrollment, DB-2.3 LAPS, DB-2.5 encryption, DB-3.2 EDR, DB-4.1 patching, DB-4.3 CA enforcement). Items with an empty `VerifiedBy` render "not checkable from the tenant" rather than letting a reader assume the assessment covers them.

**Endpoint device compliance (`DEV-*`).** `Device/Invoke-NRGDeviceCompliance.ps1` runs ON the endpoint (RMM-deployed, SYSTEM) and writes a JSON result; `Collectors/Device/Invoke-NRGCollectDeviceCompliance.ps1` ingests a folder of them behind `-DeviceResults`; `Evaluators/Test-NRGControlDevice.ps1` aggregates to one finding per control with failing hostnames in `AffectedObjects`. 35 checks defined in `Config/device-controls.json` — deliberately NOT in controls.json, which is the 202 tenant controls and a stated product number. **The endpoint script is Windows PowerShell 5.1** and is the sole carve-out from the repo-wide `#Requires -Version 7` floor; `NRG.Security.Tests.ps1` scopes that exception to the top-level `Device/` folder and asserts it earns it (no MSHTML/COM/Invoke-Expression/network). `NRG.DeviceCompliance.Tests.ps1` additionally pins: no PS7-only syntax (checked over tokenizer output, not raw text — the file's own docs mention `??`), no module import, read-only apart from the single result write, and check IDs matching device-controls.json in both directions. **Elevation honesty:** checks needing admin emit `NotAssessed`, which is excluded from the fleet denominator — never counted as a pass and never as a failure. Note the `$rows = if (...) { @(...) } else { @() }` trap: an if-block yielding an empty array assigns `$null`, so build such variables in two statements.

**Improvement plan (`-ImprovementPlan`).** `Lib/Get-NRGNISTImprovementPlan.ps1` turns the assessment from a position into a route: ordered steps against 800-53 Rev 5, each with the exact projected coverage after it, the families it moves, and what it will break. `Publishers/Publish-NRGImprovementPlan.ps1` renders Markdown + self-contained HTML. **Single framework by design** — names NIST and nothing else, tested by the same `'\b' + escape($fw)` grep the NIST matrix uses (the `\b` matters: bare `CIS` matches "precisely" and "decision" case-insensitively and the test fails on its own prose). Only the parsed NIST control IDs are rendered, never raw `FrameworkIds`, which carries every other citation.

**Improvement-plan honesty rules.** The projected score is a number a client holds you to, so: cumulative figures are recomputed from counts at each step, never accumulated from rounded per-step deltas (a test re-derives every one independently); a license-blocked control gets NO projected score and no rank, because buying a license changes the denominator and licensed-but-unconfigured is still a gap; family movement is computed by REPLAYING the plan through `Get-NRGNISTFamilyCoverage`, never by per-family arithmetic, which gets multi-family controls wrong; and `Ceiling.Note` states on page one that completing the plan is not 800-53 compliance. Two tracks: `Do now` requires a DOCUMENTED `none-visible`/`admin-review-workload`/`monitoring-integration` archetype — a control with no impact entry can never land there, since an undocumented impact is not evidence of no impact. Note `Test-NRGLicenseRequirementMet` treats `Included*` requirements as met regardless of SKU data, so "actionable implies no LicenseRequirement" is the wrong invariant; the right one is "the helper confirms it met".

**Effort classes.** Each `operational-impact.json` archetype carries an `Effort`: `Single setting` / `Single setting, then ongoing` / `Policy change` / `Policy change, then tuning` / `Staged rollout` / `Discovery first` / `Project` / `License purchase` / `Review only`. Deliberately never an hour figure — an invented hour count is a promise the tool cannot keep and the first thing a client holds you to. A test pins the allowed set and greps for `\d+\s*(h|hr|hour|day|week)`.

**System Security Plan (`-SSP`, NIST 800-171 Rev 2 / CMMC Level 2).** `Lib/Get-NRGSSPPosture.ps1` joins all 110 Rev 2 requirements from `Config/nist-800-171-r2.json` against findings; `Publishers/Publish-NRGSSP.ps1` renders Markdown + self-contained HTML + XLSX. The requirement↔control join needs NO mapping table: a CMMC practice ID embeds its 800-171 number (`IA.L2-3.5.3` → `3.5.3`) and every control already carries a CMMC citation. `Get-NRGNIST171RequirementIdsFromCmmc` matches the FULL practice-ID shape only — never bare `d.d.d`, which `Req 8.3` (PCI) would also match. Endpoint checks join through the `Nist171` array in `device-controls.json` (30 of 35 cited; 5 deliberately uncited rather than stretched). **41 of 110 requirements have automated evidence; 69 do not.**

**The SSP honesty rules — this is the one deliverable a client SIGNS.** A false `Implemented` here is a false statement in a compliance artifact handed to a C3PAO. So: a requirement with no mapped control is NEVER derived as implemented (`No automated evidence` / `Confidence: Attestation only`); a mapped control that produced no finding is `NotRun`, never a pass, and an `Error` state lands there too; a status asserted in the answers file gets `StatusSource = 'Attested'` and stays out of `Summary.ToolVerified`; `Confidence` distinguishes `Tool-verified` / `Partial evidence` / `No evidence collected` / `Attestation only`, because even an all-passing requirement is only evidenced to the extent M365 can see it. `NRG.SSP.Tests.ps1` feeds a findings set satisfying EVERY control in the tool and asserts the 69 still claim nothing.

**Answers file.** `Config/ssp/<client-slug>.psd1`, loaded by `Lib/Get-NRGSSPAnswers.ps1` via `Import-PowerShellDataFile` (data only, never executed — these get emailed between MSP and client). Shape: `System` / `Inherited` / `Requirements` with per-requirement `Status`, `Narrative`, `ResponsibleRole`, `Poam`, `NotApplicableReason`, `InheritedFrom`. `Config/ssp/example.psd1` is the template. **The entry point looks the file up by the CONNECTED domain (`$reportMetadata.TenantDomain`), not the `-TenantDomain` parameter** — under GDAP they differ and the wrong one attaches another client's narratives.

**Operational impact (`Config/operational-impact.json`).** Answers "if we enable this, what breaks?" for all 230 controls — the question that decides whether a remediation is scheduled. 27 archetypes (`legacy-client-break`, `mail-delivery-risk`, `device-gate`, `admin-elevation-friction`, …) each with `Summary`/`Users`/`Admins`/`Watchouts`/`Reversible`; every control names one; `overrides` hold per-control differences and are kept SEPARATE from the archetype, not merged over it — merging printed near-duplicate blocks differing by one sentence. `Group-NRGSSPImpact` collapses a requirement's actions to one block per archetype with the override attached as a short "X specifically" line. **A control with no entry returns `$null` and renders "Operational impact not documented" — never "no impact"**, which is the answer that gets a change approved without anyone checking.

License detection runs via `SubscribedSkus` in `Lib/Get-NRGTenantLicenseProfile.ps1`, which returns a `HashSet` of LicenseRequirement strings the tenant satisfies. `Test-NRGLicenseRequirementMet` answers per-control whether the tenant has the licenses needed. Controls whose requirement isn't met are routed to the Upgrade Unlocks section of the HTML report and do not count against the compliance score.

## Data Flow

`Connect-NRGServices` establishes Graph (24 scopes) plus EXO, Teams (optional), and IPPSSession (optional). Collectors run first and populate module-scope raw data using `Set-NRGRawData` with a key per workload. Each result object has `CollectorId`, `CollectedAt`, `Success`, and `Data`. Evaluators read raw data using `Get-NRGRawData` and write findings using `Add-NRGFinding` with states of `Satisfied`, `Gap`, `Partial`, `NotApplicable`, or `Error`. Publishers consume findings via `Get-NRGFindings`, calculate the license-aware score via `Get-NRGBaselineTier`, and produce the HTML report and JSON export.

Raw data keys and their collectors: `AAD-Inventory` set by `Invoke-NRGCollectAADInventory`; `AAD-Users` set by `Invoke-NRGCollectAADUsers`; `AAD-AuthPolicies` set by `Invoke-NRGCollectAADAuthPolicies`; `AAD-CAPolicies` set by `Invoke-NRGCollectAADAuthPolicies` via wrapper; `AAD-DirectoryRoles`, `AAD-PIMSchedules`, `AAD-IdentityGovernance` all set by `Invoke-NRGCollectAADRoles` via wrappers; `EXO-MailboxConfig` set by `Invoke-NRGCollectEXOMailboxConfig`; `EXO-ConnectionFilter` set by `Invoke-NRGCollectEXOConnectionFilter`; `Defender-Policies` set by `Invoke-NRGCollectDefender`; `DNS-domain` and `DNS-Summary` set by `Invoke-NRGCollectDNSEmailRecords`; `Teams` set by `Invoke-NRGCollectTeams`; `SharePoint` set by `Invoke-NRGCollectSharePoint`; `Intune` set by `Invoke-NRGCollectIntune`; `Purview` set by `Invoke-NRGCollectPurview`; `PowerPlatform` set by `Invoke-NRGCollectPowerPlatform`.

## Module State

All state is module-scope and cleared between batch clients by `Clear-NRGState`, which resets four variables: `NRGFindings` (List of hashtable), `NRGRawData` (Dictionary), `NRGCoverage` (Dictionary), and `NRGExceptions` (List of hashtable). `Clear-NRGState` must be called between batch clients or raw data from one client bleeds into the next client's evaluation.

## Coding Standards

Every script file requires a header block with `#Requires -Version 7.0`, the filename, NRG Technology Services / NextLayerSec LLC, Author: Matthew Levorson, a one-line purpose statement, the data keys set or consumed, and the Graph scopes or cmdlets required.

All functions use `[CmdletBinding()]`. All data structures that get serialized use `[ordered]` hashtables. All external API calls use `ErrorAction Stop` and are wrapped in `try/catch` with `Register-NRGException`. `Write-Host` is never used in collectors or evaluators — use `Write-Verbose` only. No hardcoded credentials, tenant IDs, or domain names in code. Exit codes are 0 for success, 1 for auth failure, 2 for no findings, 3 for partial collection, 4 for fatal error.

Every collector must initialize a result object with `CollectorId`, `CollectedAt`, `Success` set to `false`, and a `Data` block; execute API calls inside `try/catch`; set `Success` to `true` on completion; call `Set-NRGRawData`; and call `Register-NRGCoverage`.

Every evaluator must guard against missing data as its first action. If `Get-NRGRawData` returns null or `Success` is false, register `NotApplicable` and return immediately. Never allow a null reference to propagate into evaluation logic. `Add-NRGFinding` accepts `ControlId`, `State`, `Category`, `Title`, `Severity`, `Detail`, `FrameworkIds`, `CurrentValue`, `RequiredValue`, `Remediation` (NOT `RemediationSteps` — that parameter does not exist), and `AffectedObjects` (structured per-finding objects, e.g. recipient warn-lists or flagged inbox rules).

**Empty is not clean — `SectionStatus`.** Collectors that run several independent queries wrap each in its own `try/catch` so one failure does not abort the rest, then set `Success = $true` regardless. That makes an EMPTY list ambiguous: it can mean "queried, found nothing" (compliant) or "the query failed" (unknown), and `Success` cannot tell them apart. Any collector with independent sub-queries MUST therefore publish `Data.SectionStatus`, a map of section name to `NotRun` / `Collected` / `Failed`, and any evaluator about to conclude `Satisfied` from an empty list MUST consult it first and report `NotApplicable` when the section did not complete. Reading an empty list as compliance produced false clean bills of health on the BEC exfiltration, persistence and tenant-takeover controls — the highest-consequence class of bug this tool can have. Collectors implementing this today: `EXO-Inventory`, `AAD-DirectoryRoles`, `AAD-Inventory`, `Purview`, `PowerPlatform`. Absent `SectionStatus` is treated as collected so replayed older result JSON keeps its previous behavior.

**Empty is not the only false clean — parse the shape the API actually returns.** `SectionStatus` catches "the query failed"; it cannot catch "the query succeeded and we read the answer wrong". `Lib/Get-NRGRecipientClass.ps1` exists because the external-recipient test split on `@` and required exactly two parts, while Exchange returns `"user@dom.tld" [SMTP:user@dom.tld]` — the address **twice**, three parts, so every genuine external rule recipient was classified internal and EXO-7.2 reported clean on tenants with live exfil rules. Two rules follow. First, **classification is tri-state** (`External`/`Internal`/`Unresolved`): a boolean collapses "known internal" and "could not tell" into the safe-looking answer, so a legacy `[EX:/o=…]` DN is resolved through `Get-Recipient` and reports `Unresolved` when that fails, which the evaluator renders `NotApplicable`. Note `Unresolved` is a truthy string — callers MUST compare `-eq 'External'`, never use the value as a boolean, and a test pins that. Second, **fixtures must carry raw API shapes, not derived fields**: every fixture fed the evaluators a pre-computed `IsExternal` and so never exercised the parser, which is why it shipped broken and stayed broken. A fixture of `attacker@evil.tld` passes against the broken parser.

**Microsoft APIs OMIT optional properties — they do not null them.** Graph does not return `signInActivity` at all for a user who never signed in or last signed in before April 2020 (documented on the user resource type). Under StrictMode a nested read on an absent intermediate THROWS before `??` applies, so `$_.signInActivity.lastSignInDateTime ?? ''` failed on exactly the stale and never-signed-in accounts the guest and stale-account collectors exist to find — one such guest, which nearly every tenant has, failed the whole section, and those controls reported `NotApplicable` on every real run. Silently non-functional is the failure mode here, not falsely clean, and nothing surfaces it: `NotApplicable` is excluded from the denominator, so the score looks fine. Every nested read of API data goes through `Get-NRGNestedProperty`, enforced statically by `NRG.ExternalShapes.Tests.ps1`. A null intermediate throws identically, so there is no "safe" shape — the guard is absolute. Parse timestamps with `[datetime]::TryParse(..., [cultureinfo]::InvariantCulture, RoundtripKind, [ref]$x)`, never a bare `[datetime]` cast: this runs on whatever workstation the MSP uses.

**`Test-NRGSectionCollected`'s fallback reads a present-but-empty array as collected.** That is deliberate (replayed older JSON keeps its behaviour), but it means any collector that PRE-INITIALISES its sections to `@()` MUST publish `SectionStatus` — presence alone cannot distinguish "queried, none found" from "the query failed". `AAD-PIMSchedules` lacked it, and AAD-3.2 read the resulting empty `EligibleSchedules` as "no PIM adoption" and scored `Partial` (0.5 credit) on a privilege-escalation control. The same evaluator would also emit **`Satisfied`** — "No permanent privileged role assignments" — when `AAD-DirectoryRoles` was missing entirely, because `$permanentPriv` merely stayed empty; a verdict about role assignments requires the role data, so the evaluator now returns `NotApplicable` without it.

**A failed DNS lookup is not an absent record.** `Resolve-NRGDns` returned `@()` for any DoH response lacking an `Answer`, never reading `Status` — but Cloudflare returns SERVFAIL as HTTP 200 with `Status: 2` and no `Answer`, so a failing resolver was indistinguishable from NXDOMAIN, and the bare `return` also short-circuited the Google fallback and the `Resolve-DnsName` fallback beneath it. One transient SERVFAIL therefore produced a confident "no DMARC record", and the DNS evaluators score an absent record as a **Gap** — telling a client their email authentication is missing when it is not. Only Status `0` (NoError/NODATA) and `3` (NXDOMAIN) are authoritative "no record"; every other status falls through to the next provider. The optional `-Outcome ([ref]$x)` returns `Answered` / `NoRecord` / `LookupFailed`; the collector records it per record type in `Data.Domains.<domain>.LookupStatus`, and `Add-NRGDnsLookupFailedFinding` (one helper, not seven pasted guards) gates the seven evaluators that score absence (SPF, DKIM, DMARC, MTA-STS, TLS-RPT, DNSSEC, CAA) so a failed lookup reports `NotApplicable` **with the control's citations** — an uncited `NotApplicable` is dropped by the 800-53 family rollup as unmapped and never reaches the NIST matrix's "Not Assessed" sheet. Four rules from review of the first version. A DoH body with **no readable `Status`** (a proxy block page, a captive portal, a JSON error object — all HTTP 200) is a failure, not an answer; the first version read it as `NoRecord` and never asked the next provider. The `Resolve-DnsName` fallback reports NXDOMAIN and NODATA by **throwing**, so the catch reads the Win32 code — 9003 `DNS_ERROR_RCODE_NAME_ERROR` and 9501 `DNS_INFO_NO_RECORDS` are `NoRecord`; mapping every throw to `LookupFailed` meant that on a workstation where DoH is blocked no DNS control could ever emit a Gap. NODATA has a **second shape**: the cmdlet returns every record on the wire, so a NODATA answer can arrive as only the zone's SOA in the **Authority** section (RFC 2308 §3), and stringifying that row made a DS lookup on an unsigned zone report `Answered` — DNS-1.6 scored Satisfied. The fallback keeps only Answer-section rows of the requested type, as the DoH path already does. And `-as [int]` is far too generous for `Status`: `$null`, `''` and `$false` all cast to `0` and `2.6` rounds to `3`, so `Status` is accepted only as a whole number or a digit string, and an `XmlDocument` body (a block page that happened to be well-formed) is rejected outright because it exposes its root element as a property. The fallback renders every row in the **same text shape the DoH path returns** (`FLAGS TAG "VALUE"` for CAA, `PREF exchange` for MX, the four DS fields) — `[string]$_` on a DnsClient record gives `@{Section=Answer; Type=CAA; …}`, which the collector's CAA parse could never match, so a present CAA record scored DNS-2.2 as a false Gap on a DoH-blocked workstation; a row the fallback cannot render is a `LookupFailed`, never an `Answered` with unusable data. Win32 9701 `DNS_ERROR_RECORD_DOES_NOT_EXIST` joins 9003/9501 as an absence code. Answer rows are read through `PSObject.Properties` and a row lacking `type`/`data` is skipped rather than failing the provider. Note the DKIM control deliberately checks the customer's selector CNAMEs, not the targets: Microsoft 365 rotates DKIM keys and the inactive selector's target is routinely NXDOMAIN, so a dangling target is not a finding. `LookupStatus` is **initialised to `LookupFailed`** for every gated key and only improved by a completed lookup, because the absent-key-means-collected replay rule would otherwise let a throw between the resolver and the assignment fail the gate open on a live run. And `Resolve-NRGDns` never throws, so `-Reason ([ref]$why)` carries which providers failed and why into `$d.Errors` and the Exceptions array — without it the finding said "every resolver failed" and nothing in the results JSON said how. Coverage for `DNS-EmailRecords` is `Partial` when any lookup failed and `Failed` when all did, never `Collected` on a run in which nothing resolved — and `Failed` must be reachable on a ONE-domain tenant: the entry list is built as `@(if (...) { $map.Values } else { $map })` with the `@()` around the whole `if`, because an if-statement unrolls the array it yields and the lone hashtable's `.Count` is its key count (the `$rows = if (...)` trap again). The collector validates every outcome before writing it — only `Answered`/`NoRecord` may improve on the `LookupFailed` default, since `Test-NRGDnsLookupSucceeded` reads a blank as collected — and every per-record `catch` records the throw in `Errors` and the Exceptions array; an empty `catch { }` beside a coverage note that says "see Exceptions" is a lie. `NRG.DnsCollector.Tests.ps1` pins all of this by injecting a mock resolver into module scope (`Set-Item function:script:` via `& $module {}`), which is the only way to intercept a call made from inside the module. Absent `LookupStatus` counts as collected, so replayed older JSON keeps its behaviour. Pinned in both directions by `NRG.DnsResolution.Tests.ps1` for all seven controls: `LookupFailed` must not score, `NoRecord` must still be a Gap, and the replay fixture omits the key rather than passing an empty map.

**An unassessed control is invisible unless something names it — `Get-NRGAssessmentScope`.** `NotApplicable` is excluded from the compliance denominator, which is correct, but it means a control that silently stops producing a verdict makes the score go **UP**. That is the shape of every high-consequence bug this tool has had: the omitted `signInActivity` property, the missing `AAD-PIMSchedules` SectionStatus, the DNS lookup read as an absent record. In each case the score looked fine and nothing in the deliverable said the control had gone quiet. `Lib/Get-NRGAssessmentScope.ps1` is the surface that says it, rendered as the **Assessment Scope and Limitations** section in the HTML report (`id="scope"`, directly under the score) and the Markdown summary. It sorts every control in `controls.json` into exactly one bucket — scored, `LicenceBlocked` (benign, already priced under Upgrade Unlocks), `CollectionIncomplete` (**the dangerous one**: the control could have been assessed and was not), `NoProgrammaticCheck` (advisory, honest by design but it must be visible rather than implied), or `NoResult` (**worse still**: the control emitted nothing at all, so it is absent from the report entirely) — and it is the only place that computes the set difference `controls.json − findings`. Three rules. It is a **view, not a verdict**: it emits no findings and moves no score, and `NRG.AssessmentScope.Tests.ps1` pins both. The buckets must **sum to the unscored count** with no control in two of them, because a control that is unscored and in no bucket is exactly the failure mode the section exists to end. And the limitations text **never reassures** — a test greps it for "is compliant", "no issues found" and friends. For a control with several instance findings (DNS per domain, the named-object evaluators) the **worst** state wins: assessed on one domain and not another is "partly", and partly is the honest answer.

**Absence of evidence is never evidence — the classifier's ordering rule.** The first version of `Get-NRGAssessmentScope` inverted `Test-NRGLicenseRequirementMet`, which returns `$false` when there is **no SKU data at all** (deliberately, so Upgrade Unlocks over-reports an upgrade need rather than hiding one). Inverted, "we cannot tell how this tenant is licensed" became "licence gated, benign" — so on any run where the licence profile did not populate, including every `-FromResults` republish, controls whose own `Detail` read *"EXO data not collected"* were filed as benign. The honesty section had the dishonesty bug. Every signal is therefore consulted only when **positively present**, strongest first: (1) the evaluator's own `requires manual verification` marker, which is authoritative about itself; (2) **hard evidence** — the control's `CollectorDependency` raw-data key is absent or its `Success` is false, the same signal the evaluator gated on, used **only when raw data is actually populated**, since an empty map means replay, not universal failure; (3) licence, only on the evaluators' explicit `upgrade opportunity` marker or a profile carrying real SKU data; (4) last and weakest, the evaluator's prose. The prose patterns are **derived empirically** — every evaluator is run against empty state and the distinct `Detail` strings collected — never invented to match the regex, which is how *"Teams collector did not run."* and *"Neither AAD-Users nor AAD-AuthPolicies collector produced data."* went unmatched and were reported as "no automated test". `NRG.AssessmentScope.Tests.ps1` drives the real 179 evaluators with no data and asserts every resulting `NotApplicable` lands in collection-failed or self-declared-advisory and that **nothing** is called licence gated. `-Quick` deliberately drops evaluators, so their controls get their own `NotEvaluatedThisMode` bucket rather than `NoResult`'s "treat this as a tool fault". `-FromResults` restores `Coverage` and `RawData` into module state before publishing, because a republish that silently loses them looks cleaner than the run it reprints.

**Application permissions are the half of app risk the delegated table cannot see — `AAD-15.1` / `AAD-15.2`.** AAD-12.4 reads `oauth2PermissionGrants` with consentType `AllPrincipals`. That is the **delegated** consent table: an app acting as a signed-in user. An app-only grant is an **`appRoleAssignment`** and does not appear there at all, so a malicious application permission returns ZERO rows from the endpoint AAD-12.4 queries and the report says the tenant is clean. `Collectors/AAD/Invoke-NRGCollectAADAppPermissions.ps1` reads the other table. The distinction is the whole point: an application permission is exercised with **no signed-in user**, so no MFA prompt fires, no Conditional Access policy applies (there is no sign-in to attach one to), and the activity does not look like a person in the sign-in logs. `Mail.ReadWrite` app-only reads every mailbox; `RoleManagement.ReadWrite.Directory` makes the app Global Administrator; `Domain.ReadWrite.All` adds a federated domain and forges tokens for anyone. Collection asks each high-value RESOURCE who holds a role on it (`/servicePrincipals/{id}/appRoleAssignedTo` for Graph, Exchange and SharePoint) rather than asking every principal what it holds — three paged queries instead of hundreds. **No new Graph scope**: `Application.Read.All`, `Directory.Read.All` and `Organization.Read.All` are already requested, so this needs no re-consent in any client tenant, and a test asserts that. Four rules. `Config/app-permissions-risk.json` holds the judgement as reviewable data, tier 1 (takeover) and tier 2 (mass data access), each entry carrying the reason it is rated; a permission in neither tier is **collected and reported but not scored**, because absence from the catalog means unrated, never safe. Microsoft first-party apps legitimately hold these, so they are excluded from the VERDICT and their count is **stated in the detail** — set aside, never silently dropped — while an app whose owner cannot be determined is scored, not waved through. `SectionStatus` is per resource and **every** watched resource must read `Collected` before either control will reach a verdict: Exchange is where `full_access_as_app` lives, so scoring Graph alone and calling it clean would miss the worst grant in the product. And `@odata.nextLink` must be read with `Get-NRGObjectField`, **never `Get-NRGNestedProperty`**, which splits its path on `.` and resolves `@odata` → `nextLink`, returning the default so paging silently stops after page one and a partial list is reported as a full enumeration.

**Read new fields through `Get-NRGObjectField`, including your own.** The StrictMode rule is not only about external cmdlet output: result JSON replayed from an earlier run does not carry fields added since, so dot-accessing a field you just introduced throws on every older results file.

**Advisory controls never claim compliance.** A control with no programmatic check must emit `NotApplicable`, never `Satisfied` or `Partial`. `Partial` is worth 0.5 toward the compliance score, so an advisory control scored as `Partial` hands every tenant free credit for a verdict the tool never computed. Enforced statically by `NRG.EvaluatorHonesty.Tests.ps1`.

**US English spelling.** This tool produces deliverables for US clients, so all prose — findings text, remediation guidance, `Config/*.json` strings, comments and docs — uses US spelling: `license` not `licence`, and likewise `organization`, `behavior`, `defense`, `enrollment`, `catalog`, `analyze`, `normalize`, `authorized`, `sanitized`, `labeled`, `gray`. A British spelling reaching a client report reads as careless, and mixed spellings inside one document read worse. Note `Effort: 'License purchase'` in `Config/operational-impact.json` is pinned by `NRG.ImprovementPlan.Tests.ps1` — the config value and the test's allowed set must change together.

**StrictMode.** `Set-StrictMode -Version Latest` is active module-wide. Referencing a property an object does not have THROWS before a `??` default can apply, so fields read off external cmdlet output whose shape is not guaranteed must go through `Get-NRGObjectField`, not direct dot-access.

## Batch Mode

`Config/clients.json` requires the following fields for every client: `ClientName`, `TenantDomain`, `TenantId` (GUID), `DelegatedOrg` (the `.onmicrosoft.com` routing domain — not the primary domain), `DnsDomains` (array), `SkipPurview`, `SkipTeams`, `SkipSharePoint`, `SkipIntune`, `SkipPowerPlatform`, `SkipDNS` (all boolean), `Notes`, and `Active`.

## Common Tasks

**To add a new control:** add the entry to `Config/controls.json` with all required fields including `LicenseRequirement`, add the evaluator function to the appropriate file in `Evaluators/`, verify the function name matches `EvaluatorFunction`, verify the collector sets the data key referenced by `CollectorDependency`, and add the new function name to both `FunctionsToExport` in `NRG-Assessment.psd1` and `$script:ExportedFunctions` in `NRG-Assessment.psm1`.

**To add a new client:** get the `TenantId` from the OpenID configuration endpoint, confirm the `.onmicrosoft.com` routing domain from M365 Admin Center, add the entry to `clients.json`, and set Skip flags based on the client's license tier — set `SkipPurview` and `SkipPowerPlatform` for Business Standard clients.

**To debug a collector:** run `-JsonOnly`, open the output JSON, find the collector key under `RawData`, check the `Success` field and `CollectedAt` timestamp, and check the `Exceptions` array for registered errors.

**To debug a wrong evaluator result:** confirm what raw data key it reads, verify the collector set `Success` to `true`, and inspect the specific fields the evaluator accesses against the actual collected data. Evaluators must never crash on missing fields — use null-conditional operators or explicit null checks throughout.

## Security Requirements

The tool is **read-only without exception**. No evaluator, collector, or publisher may write to tenant configuration. All Graph calls use GET only. All EXO calls use read-only cmdlets only. Any future write capability belongs exclusively in `Apply-NRGBaseline.ps1` with mandatory `WhatIf` support. Raw data is stored in module-scope memory only and never written to disk unencrypted. JSON output must not include credentials, tokens, or user PII beyond UPN and display name.
