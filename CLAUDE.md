# NRG-Assessment Tool — Claude Code Project Context

**Author:** NRG Technology Services — nrgtechservices.com
**GitHub:** https://github.com/Blackvectra/NRG-Assessment-Tool
**Version:** 4.12.1
**Language:** PowerShell 7.0+
**Purpose:** Read-only Microsoft 365 security assessment framework for MSP multi-tenant environments.

## What This Tool Does

NRG-Assessment runs agentlessly against any Microsoft 365 tenant, collects security configuration data via Microsoft Graph and Exchange Online PowerShell, evaluates 202 controls against a license-aware baseline, and produces an interactive HTML report with executive summary, compliance matrix, attack scenario analysis, and NRG services pitch. It is a read-only assessment — it never modifies tenant configuration.

There are four entry points. `Invoke-NRGAssessment.ps1` runs against a single tenant interactively. `Invoke-NRGBatchAssessment.ps1` runs against all clients defined in `Config/clients.json` sequentially using GDAP delegated access, producing per-client reports and a batch summary. `Invoke-NRGSignInTriage.ps1` (v4.12.0) runs admin-scope sign-in IoC triage to rank likely-compromised users. `Invoke-NRGEmailAssessment.ps1` (v4.12.0) runs a per-user mailbox incident-response deep-dive.

The v4.12.0 Email-IR mode lives in the top-level `Email-IR/` subtree (`Lib/`, `Collectors/`, `Evaluators/`, `Publishers/`, `Testing/`), auto-loaded by the psm1 `$loadOrder`. Its evaluators use `EMAIL-*` and `SIGNIN-*` control IDs and are not in `Config/controls.json` — they are heuristic IoC checks, not baseline controls.

## Control Architecture

202 total controls across 9 workloads: Azure AD / Entra ID (AAD, 47), Exchange Online (EXO, 35), Defender for Office 365 (DEF, 24), Microsoft Teams (TMS, 22), SharePoint Online (SPO, 18), Purview / Compliance (PVW, 18), Microsoft Intune (INT, 17), Power Platform (PPL, 11), Email Auth DNS (DNS, 10). Severity breakdown: 12 Critical, 96 High, 67 Medium, 27 Low.

License-aware scoring is encoded per control via the `LicenseRequirement` string field in `controls.json` (e.g. "M365 Business Premium or Entra ID P1", "Defender for Office 365 P1", "E5 Compliance"). There are no separate per-tier baseline JSON files — the requirement lives on each control row.

**NIST SP 800-53 Rev 5 rollup.** All 202 controls carry a `References.NIST` citation, spanning 12 of the 20 800-53 families. `Lib/Get-NRGNISTFamilyCoverage.ps1` rolls findings up by control family (AC, AU, IA, SC, SI, …) and by individual 800-53 control, using the same score formula and denominator rules as `Get-NRGCoverageScore`. It parses the `NIST:` prefix off the flattened `FrameworkIds` string — never the bare identifier shape, which would also match CMMC's `IA.L2-3.5.3`. A finding citing controls in two families is counted in each, so family rows deliberately do not sum to the assessment total; every surface that renders them says so. The rollup appears in the HTML report (`id="nist-families"`), the Markdown summary, and a dedicated `NIST Families` sheet in the XLSX matrix. `NRG.NISTFamily.Tests.ps1` pins both the parsing and the controls.json invariant that every control carries a parseable NIST citation — a control missing one vanishes from the family view, shrinking that family's denominator and inflating its coverage.

**Report framework selection.** `Invoke-NRGAssessment.ps1 -Framework <NIST|CIS|SCuBA|CMMC|All>` decides which framework cards the HTML report shows. **NRG defaults to `NIST`; NLS defaults to `All`** — the single deliberate behavioural difference between the twins, pinned in each repo by `NRG.FrameworkDefault.Tests.ps1` because a careless mirror would silently flip it and the failure would be invisible (the report still renders and still scores correctly). The PUBLISHER default stays `@('CIS','SCuBA','NIST','CMMC')` in both; only the entry point differs, so direct callers and the other twin are unaffected. Narrowing is presentation only: `Publish-NRGAssessmentHTML` scores all four regardless of `-Frameworks`, controls.json keeps every citation, and a test asserts no framework score moves when the report narrows. The `.fw-grid` column count is interpolated from the displayed set — hardcoding 4 renders a single card at quarter width. `Publish-NRGNISTMatrix` also emits a **NIST-only HTML report** (alongside Markdown and XLSX) that mentions no other framework anywhere on the page; a test greps for CIS/SCuBA/CMMC/ISO/SOC/HIPAA/PCI/MITRE and fails on any leak.

**Standalone NIST matrix.** `Publish-NRGNISTMatrix.ps1` emits a single-framework 800-53 Rev 5 deliverable (Markdown always, XLSX via openpyxl) behind the `-NISTMatrix` switch on `Invoke-NRGAssessment.ps1`; `-AllFiles` implies it. Six sheets: Summary, Control Matrix (one row per 800-53 control x tool control), By Control, By Family, Physical & Device, Not Assessed. Official Rev 5 titles come from `Config/nist-800-53-catalog.json` via `Lib/Get-NRGNISTControlCatalog.ps1` — note the Rev 4 -> Rev 5 renames the tool cites (AC-11 Device Lock, AT-2 Literacy Training and Awareness, AU-2 Event Logging, AU-4 Audit Log Storage Capacity, AC-6(9) Log Use of Privileged Functions, AC-16 Security and Privacy Attributes); `NRG.NISTMatrix.Tests.ps1` pins them by name. **The matrix is strictly additive** — `Publish-NRGComplianceMatrix` keeps all ten frameworks and no existing output changes; a test asserts publishing it does not move the CIS/SCuBA/CMMC scores. Every rollup table carries an Error column so Met + Partial + Gap + Error + N/A sums to Assessed; without it a reader who adds a row up comes short and has no way to tell whether the missing rows were passes or failures.

**NIST physical / media / device controls.** `Config/nist-physical.json` defines 31 800-53 controls covering endpoint posture, media, maintenance, personnel, and physical/environmental protection, each with the device aspect it covers and two or more implementation options. `Lib/Get-NRGNISTPhysicalPosture.ps1` joins it against findings and renders in the HTML report (`id="nist-physical"`) and the Markdown summary. Each item declares a `Scope`: `Tenant` (10, fully evidenced by scored controls), `Hybrid` (7, partly evidenced, remainder off-tenant), or `Attested` (14, not observable from Microsoft 365 at all). **Nothing in this section is scored** — Tenant/Hybrid rows reflect findings already scored under their own control IDs, and `Attested` rows always report `Attestation required`, never a compliance state. That is the "advisory controls never claim compliance" rule applied to a whole section: the section exists so a reader cannot infer from a clean NIST family table that the physical families were assessed and passed. `NRG.NISTPhysical.Tests.ps1` enforces the scope contracts (Tenant must cite evidence controls; Hybrid must cite both halves; Attested must name the off-tenant evidence and cite none), verifies every `EvidenceControls` ID exists in `controls.json`, and feeds the posture a findings set that satisfies every control in the tool to prove the attested rows still refuse to claim anything.

**Device guide (no scanning).** `Publishers/Publish-NRGDeviceGuide.ps1` renders `Config/nist-physical.json` into a printable device/endpoint guide — 31 controls, 98 implementation options, Markdown plus self-contained HTML with print styling and no external assets. `New-NRGDeviceGuide.ps1` is its standalone entry point and **connects to nothing**: no sign-in, no Graph, no EXO, no endpoint access, so the guide is usable before a tenant is attached. `-ResultsPath` optionally annotates it with a prior run's verdicts. Two invariants are statically enforced by `NRG.DeviceGuide.Tests.ps1`: neither file may reference `Invoke-NRGGraphRequest` / `Connect-MgGraph` / `Invoke-RestMethod` / `Get-NRGRawData` etc., and supplying findings must not change the rendered options (a test diffs them with and without). Note `@($null).Count` is 1, not 0 — counting an omitted `-Findings` that way made the guide print "Assessment result: Not assessed" for controls nothing had assessed; strip nulls before counting.

**Device build standard.** `Config/device-baseline.json` holds 27 lifecycle requirements (procure / provision / harden / in-service / offboard), 23 mandatory, each with Why, How, `Nist` citations and `VerifiedBy` tool-control references. `Publishers/Publish-NRGDeviceBaseline.ps1` renders it as a printable checklist plus detail; `New-NRGDeviceGuide.ps1` emits it alongside the control reference as `<base>-baseline.md`/`.html`. Same no-network contract as the guide, statically enforced. `NRG.DeviceBaseline.Tests.ps1` verifies every `VerifiedBy` exists in controls.json and every `Nist` entry resolves in the 800-53 catalog — both rot silently as the tool changes — and pins the mandatory set (DB-2.1 enrolment, DB-2.3 LAPS, DB-2.5 encryption, DB-3.2 EDR, DB-4.1 patching, DB-4.3 CA enforcement). Items with an empty `VerifiedBy` render "not checkable from the tenant" rather than letting a reader assume the assessment covers them.

**Endpoint device compliance (`DEV-*`).** `Device/Invoke-NRGDeviceCompliance.ps1` runs ON the endpoint (RMM-deployed, SYSTEM) and writes a JSON result; `Collectors/Device/Invoke-NRGCollectDeviceCompliance.ps1` ingests a folder of them behind `-DeviceResults`; `Evaluators/Test-NRGControlDevice.ps1` aggregates to one finding per control with failing hostnames in `AffectedObjects`. 35 checks defined in `Config/device-controls.json` — deliberately NOT in controls.json, which is the 202 tenant controls and a stated product number. **The endpoint script is Windows PowerShell 5.1** and is the sole carve-out from the repo-wide `#Requires -Version 7` floor; `NRG.Security.Tests.ps1` scopes that exception to the top-level `Device/` folder and asserts it earns it (no MSHTML/COM/Invoke-Expression/network). `NRG.DeviceCompliance.Tests.ps1` additionally pins: no PS7-only syntax (checked over tokenizer output, not raw text — the file's own docs mention `??`), no module import, read-only apart from the single result write, and check IDs matching device-controls.json in both directions. **Elevation honesty:** checks needing admin emit `NotAssessed`, which is excluded from the fleet denominator — never counted as a pass and never as a failure. Note the `$rows = if (...) { @(...) } else { @() }` trap: an if-block yielding an empty array assigns `$null`, so build such variables in two statements.

**Improvement plan (`-ImprovementPlan`).** `Lib/Get-NRGNISTImprovementPlan.ps1` turns the assessment from a position into a route: ordered steps against 800-53 Rev 5, each with the exact projected coverage after it, the families it moves, and what it will break. `Publishers/Publish-NRGImprovementPlan.ps1` renders Markdown + self-contained HTML. **Single framework by design** — names NIST and nothing else, tested by the same `'\b' + escape($fw)` grep the NIST matrix uses (the `\b` matters: bare `CIS` matches "precisely" and "decision" case-insensitively and the test fails on its own prose). Only the parsed NIST control IDs are rendered, never raw `FrameworkIds`, which carries every other citation.

**Improvement-plan honesty rules.** The projected score is a number a client holds you to, so: cumulative figures are recomputed from counts at each step, never accumulated from rounded per-step deltas (a test re-derives every one independently); a licence-blocked control gets NO projected score and no rank, because buying a licence changes the denominator and licensed-but-unconfigured is still a gap; family movement is computed by REPLAYING the plan through `Get-NRGNISTFamilyCoverage`, never by per-family arithmetic, which gets multi-family controls wrong; and `Ceiling.Note` states on page one that completing the plan is not 800-53 compliance. Two tracks: `Do now` requires a DOCUMENTED `none-visible`/`admin-review-workload`/`monitoring-integration` archetype — a control with no impact entry can never land there, since an undocumented impact is not evidence of no impact. Note `Test-NRGLicenseRequirementMet` treats `Included*` requirements as met regardless of SKU data, so "actionable implies no LicenseRequirement" is the wrong invariant; the right one is "the helper confirms it met".

**Effort classes.** Each `operational-impact.json` archetype carries an `Effort`: `Single setting` / `Single setting, then ongoing` / `Policy change` / `Policy change, then tuning` / `Staged rollout` / `Discovery first` / `Project` / `Licence purchase` / `Review only`. Deliberately never an hour figure — an invented hour count is a promise the tool cannot keep and the first thing a client holds you to. A test pins the allowed set and greps for `\d+\s*(h|hr|hour|day|week)`.

**System Security Plan (`-SSP`, NIST 800-171 Rev 2 / CMMC Level 2).** `Lib/Get-NRGSSPPosture.ps1` joins all 110 Rev 2 requirements from `Config/nist-800-171-r2.json` against findings; `Publishers/Publish-NRGSSP.ps1` renders Markdown + self-contained HTML + XLSX. The requirement↔control join needs NO mapping table: a CMMC practice ID embeds its 800-171 number (`IA.L2-3.5.3` → `3.5.3`) and every control already carries a CMMC citation. `Get-NRGNIST171RequirementIdsFromCmmc` matches the FULL practice-ID shape only — never bare `d.d.d`, which `Req 8.3` (PCI) would also match. Endpoint checks join through the `Nist171` array in `device-controls.json` (30 of 35 cited; 5 deliberately uncited rather than stretched). **41 of 110 requirements have automated evidence; 69 do not.**

**The SSP honesty rules — this is the one deliverable a client SIGNS.** A false `Implemented` here is a false statement in a compliance artifact handed to a C3PAO. So: a requirement with no mapped control is NEVER derived as implemented (`No automated evidence` / `Confidence: Attestation only`); a mapped control that produced no finding is `NotRun`, never a pass, and an `Error` state lands there too; a status asserted in the answers file gets `StatusSource = 'Attested'` and stays out of `Summary.ToolVerified`; `Confidence` distinguishes `Tool-verified` / `Partial evidence` / `No evidence collected` / `Attestation only`, because even an all-passing requirement is only evidenced to the extent M365 can see it. `NRG.SSP.Tests.ps1` feeds a findings set satisfying EVERY control in the tool and asserts the 69 still claim nothing.

**Answers file.** `Config/ssp/<client-slug>.psd1`, loaded by `Lib/Get-NRGSSPAnswers.ps1` via `Import-PowerShellDataFile` (data only, never executed — these get emailed between MSP and client). Shape: `System` / `Inherited` / `Requirements` with per-requirement `Status`, `Narrative`, `ResponsibleRole`, `Poam`, `NotApplicableReason`, `InheritedFrom`. `Config/ssp/example.psd1` is the template. **The entry point looks the file up by the CONNECTED domain (`$reportMetadata.TenantDomain`), not the `-TenantDomain` parameter** — under GDAP they differ and the wrong one attaches another client's narratives.

**Operational impact (`Config/operational-impact.json`).** Answers "if we enable this, what breaks?" for all 230 controls — the question that decides whether a remediation is scheduled. 27 archetypes (`legacy-client-break`, `mail-delivery-risk`, `device-gate`, `admin-elevation-friction`, …) each with `Summary`/`Users`/`Admins`/`Watchouts`/`Reversible`; every control names one; `overrides` hold per-control differences and are kept SEPARATE from the archetype, not merged over it — merging printed near-duplicate blocks differing by one sentence. `Group-NRGSSPImpact` collapses a requirement's actions to one block per archetype with the override attached as a short "X specifically" line. **A control with no entry returns `$null` and renders "Operational impact not documented" — never "no impact"**, which is the answer that gets a change approved without anyone checking.

License detection runs via `SubscribedSkus` in `Lib/Get-NRGTenantLicenseProfile.ps1`, which returns a `HashSet` of LicenseRequirement strings the tenant satisfies. `Test-NRGLicenseRequirementMet` answers per-control whether the tenant has the licenses needed. Controls whose requirement isn't met are routed to the Upgrade Unlocks section of the HTML report and do not count against the compliance score.

## Data Flow

`Connect-NRGServices` establishes Graph (24 scopes) plus EXO, Teams (optional), and IPPSSession (optional). Collectors run first and populate module-scope raw data using `Set-NRGRawData` with a key per workload. Each result object has `CollectorId`, `CollectedAt`, `Success`, and `Data`. Evaluators read raw data using `Get-NRGRawData` and write findings using `Add-NRGFinding` with states of `Satisfied`, `Gap`, `Partial`, `NotApplicable`, or `Error`. Publishers consume findings via `Get-NRGFindings`, calculate the license-aware score via `Get-NRGBaselineTier`, and produce the HTML report and JSON export.

Raw data keys and their collectors: `AAD-Inventory` set by `Invoke-NRGCollectAADInventory`; `AAD-Users` set by `Invoke-NRGCollectAADUsers`; `AAD-AuthPolicies` set by `Invoke-NRGCollectAADAuthPolicies`; `AAD-CAPolicies` set by `Invoke-NRGCollectAADAuthPolicies` via wrapper; `AAD-DirectoryRoles`, `AAD-PIMSchedules`, `AAD-IdentityGovernance` all set by `Invoke-NRGCollectAADRoles` via wrappers; `EXO-MailboxConfig` set by `Invoke-NRGCollectEXOMailboxConfig`; `EXO-ConnectionFilter` set by `Invoke-NRGCollectEXOConnectionFilter`; `Defender-Policies` set by `Invoke-NRGCollectDefender`; `DNS-domain` and `DNS-Summary` set by `Invoke-NRGCollectDNSEmailRecords`; `Teams` set by `Invoke-NRGCollectTeams`; `SharePoint` set by `Invoke-NRGCollectSharePoint`; `Intune` set by `Invoke-NRGCollectIntune`; `Purview` set by `Invoke-NRGCollectPurview`; `PowerPlatform` set by `Invoke-NRGCollectPowerPlatform`.

## Module State

All state is module-scope and cleared between batch clients by `Clear-NRGState`, which resets four variables: `NRGFindings` (List of hashtable), `NRGRawData` (Dictionary), `NRGCoverage` (Dictionary), and `NRGExceptions` (List of hashtable). `Clear-NRGState` must be called between batch clients or raw data from one client bleeds into the next client's evaluation.

## Coding Standards

Every script file requires a header block with `#Requires -Version 7.0`, the filename, NRG Technology Services / NextLayerSec LLC, Author: Matthew Levorson, a one-line purpose statement, the data keys set or consumed, and the Graph scopes or cmdlets required.

All functions use `[CmdletBinding()]`. All data structures that get serialized use `[ordered]` hashtables. All external API calls use `ErrorAction Stop` and are wrapped in `try/catch` with `Register-NRGException`. `Write-Host` is never used in collectors or evaluators — use `Write-Verbose` only. No hardcoded credentials, tenant IDs, or domain names in code. Exit codes are 0 for success, 1 for auth failure, 2 for no findings, 3 for partial collection, 4 for fatal error.

Every collector must initialize a result object with `CollectorId`, `CollectedAt`, `Success` set to `false`, and a `Data` block; execute API calls inside `try/catch`; set `Success` to `true` on completion; call `Set-NRGRawData`; and call `Register-NRGCoverage`.

Every evaluator must guard against missing data as its first action. If `Get-NRGRawData` returns null or `Success` is false, register `NotApplicable` and return immediately. Never allow a null reference to propagate into evaluation logic. `Add-NRGFinding` accepts `ControlId`, `State`, `Category`, `Title`, `Severity`, `Detail`, `FrameworkIds`, `CurrentValue`, `RequiredValue`, `Remediation` (NOT `RemediationSteps` — that parameter does not exist), and `AffectedObjects` (structured per-finding objects, e.g. recipient warn-lists or flagged inbox rules).

**Empty is not clean — `SectionStatus`.** Collectors that run several independent queries wrap each in its own `try/catch` so one failure does not abort the rest, then set `Success = $true` regardless. That makes an EMPTY list ambiguous: it can mean "queried, found nothing" (compliant) or "the query failed" (unknown), and `Success` cannot tell them apart. Any collector with independent sub-queries MUST therefore publish `Data.SectionStatus`, a map of section name to `NotRun` / `Collected` / `Failed`, and any evaluator about to conclude `Satisfied` from an empty list MUST consult it first and report `NotApplicable` when the section did not complete. Reading an empty list as compliance produced false clean bills of health on the BEC exfiltration, persistence and tenant-takeover controls — the highest-consequence class of bug this tool can have. Collectors implementing this today: `EXO-Inventory`, `AAD-DirectoryRoles`, `AAD-Inventory`, `Purview`, `PowerPlatform`. Absent `SectionStatus` is treated as collected so replayed older result JSON keeps its previous behaviour.

**Empty is not the only false clean — parse the shape the API actually returns.** `SectionStatus` catches "the query failed"; it cannot catch "the query succeeded and we read the answer wrong". `Lib/Get-NRGRecipientClass.ps1` exists because the external-recipient test split on `@` and required exactly two parts, while Exchange returns `"user@dom.tld" [SMTP:user@dom.tld]` — the address **twice**, three parts, so every genuine external rule recipient was classified internal and EXO-7.2 reported clean on tenants with live exfil rules. Two rules follow. First, **classification is tri-state** (`External`/`Internal`/`Unresolved`): a boolean collapses "known internal" and "could not tell" into the safe-looking answer, so a legacy `[EX:/o=…]` DN is resolved through `Get-Recipient` and reports `Unresolved` when that fails, which the evaluator renders `NotApplicable`. Note `Unresolved` is a truthy string — callers MUST compare `-eq 'External'`, never use the value as a boolean, and a test pins that. Second, **fixtures must carry raw API shapes, not derived fields**: every fixture fed the evaluators a pre-computed `IsExternal` and so never exercised the parser, which is why it shipped broken and stayed broken. A fixture of `attacker@evil.tld` passes against the broken parser.

**Read new fields through `Get-NRGObjectField`, including your own.** The StrictMode rule is not only about external cmdlet output: result JSON replayed from an earlier run does not carry fields added since, so dot-accessing a field you just introduced throws on every older results file.

**Advisory controls never claim compliance.** A control with no programmatic check must emit `NotApplicable`, never `Satisfied` or `Partial`. `Partial` is worth 0.5 toward the compliance score, so an advisory control scored as `Partial` hands every tenant free credit for a verdict the tool never computed. Enforced statically by `NRG.EvaluatorHonesty.Tests.ps1`.

**StrictMode.** `Set-StrictMode -Version Latest` is active module-wide. Referencing a property an object does not have THROWS before a `??` default can apply, so fields read off external cmdlet output whose shape is not guaranteed must go through `Get-NRGObjectField`, not direct dot-access.

## Control Schema

Each entry in `Config/controls.json` is validated by `Config/schema/controls.schema.json`. Required fields: `ControlId` (workload-prefixed, e.g. `AAD-1.1`), `Title`, `Description`, `BusinessRisk`, `Severity` (`Critical|High|Medium|Low|Informational`), `Workload` (one of AAD, EXO, DEF, TMS, PVW, SPO, INT, PPL, DNS), `Category`, `Automated` (boolean), `CollectorDependency` (raw-data key name the evaluator depends on), `EvaluatorFunction` (function name in `Evaluators/`), `Remediation`, `References` (array of framework citations), `LicenseRequirement` (string matched against `Get-NRGTenantLicenseProfile` output).

## Batch Mode

`Config/clients.json` requires the following fields for every client: `ClientName`, `TenantDomain`, `TenantId` (GUID), `DelegatedOrg` (the `.onmicrosoft.com` routing domain — not the primary domain), `DnsDomains` (array), `SkipPurview`, `SkipTeams`, `SkipSharePoint`, `SkipIntune`, `SkipPowerPlatform`, `SkipDNS` (all boolean), `Notes`, and `Active`.

`DelegatedOrg` must be the `.onmicrosoft.com` routing domain. Get it from Microsoft 365 Admin Center under Settings then Domains for each client. Get `TenantId` from `https://login.microsoftonline.com/domain/.well-known/openid-configuration` — the GUID in the issuer field is the TenantId.

Test sequence before first full run: run with `-WhatIf` first, then `-OnlyClient nrgtechservices.com -JsonOnly`, then full batch.

## Common Tasks

**To add a new control:** add the entry to `Config/controls.json` with all required fields including `LicenseRequirement`, add the evaluator function to the appropriate file in `Evaluators/`, verify the function name matches `EvaluatorFunction`, verify the collector sets the data key referenced by `CollectorDependency`, and add the new function name to both `FunctionsToExport` in `NRG-Assessment.psd1` and `$script:ExportedFunctions` in `NRG-Assessment.psm1`.

**To add a new client:** get the `TenantId` from the OpenID configuration endpoint, confirm the `.onmicrosoft.com` routing domain from M365 Admin Center, add the entry to `clients.json`, and set Skip flags based on the client's license tier — set `SkipPurview` and `SkipPowerPlatform` for Business Standard clients.

**To debug a collector:** run `-JsonOnly`, open the output JSON, find the collector key under `RawData`, check the `Success` field and `CollectedAt` timestamp, and check the `Exceptions` array for registered errors.

**To debug a wrong evaluator result:** confirm what raw data key it reads, verify the collector set `Success` to `true`, and inspect the specific fields the evaluator accesses against the actual collected data. Evaluators must never crash on missing fields — use null-conditional operators or explicit null checks throughout.

## Security Requirements

The tool is **read-only without exception**. No evaluator, collector, or publisher may write to tenant configuration. All Graph calls use GET only. All EXO calls use read-only cmdlets only. Any future write capability belongs exclusively in `Apply-NRGBaseline.ps1` with mandatory `WhatIf` support. Raw data is stored in module-scope memory only and never written to disk unencrypted. JSON output must not include credentials, tokens, or user PII beyond UPN and display name.
