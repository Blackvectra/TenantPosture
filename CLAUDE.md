# TenantPosture Tool — Claude Code Project Context

**Author:** Matthew Levorson — NextLayerSec LLC (support@nextlayersec.dev)
**GitHub:** https://github.com/Blackvectra/TenantPosture
**Version:** 4.14.3
**Language:** PowerShell 7.0+ (the module floor; Exchange Online and Purview sessions need 7.4 or later, see `Get-TPExoModuleFloor`)
**Purpose:** Read-only Microsoft 365 security assessment framework for MSP multi-tenant environments.

## What This Tool Does

TenantPosture runs agentlessly against any Microsoft 365 tenant, collects security configuration data via Microsoft Graph and Exchange Online PowerShell, evaluates 253 controls against a license-aware baseline, and produces an interactive HTML report with executive summary, compliance matrix, attack scenario analysis, and NRG services pitch. It is a read-only assessment — it never modifies tenant configuration.

There are four entry points. `Invoke-TPAssessment.ps1` runs against a single tenant interactively. `Invoke-TPBatchAssessment.ps1` runs against all clients defined in `Config/clients.json` sequentially using GDAP delegated access, producing per-client reports and a batch summary. `Invoke-TPSignInTriage.ps1` (v4.12.0) runs admin-scope sign-in IoC triage to rank likely-compromised users. `Invoke-TPEmailAssessment.ps1` (v4.12.0) runs a per-user mailbox incident-response deep-dive. `Compare-TPTenantBaseline.ps1` is a standalone offline tool, not an assessment: it compares two tenants' results JSON files against the NRG Security Baseline and connects to nothing. `New-TPFleetDashboard.ps1` (every client's saved runs on one page) and `New-TPRemediationProof.ps1` (a proof-of-fix certificate from two runs of one tenant) are offline in the same way.

The v4.12.0 Email-IR mode lives in the top-level `Email-IR/` subtree (`Lib/`, `Collectors/`, `Evaluators/`, `Publishers/`, `Testing/`), auto-loaded by the psm1 `$loadOrder`. Its evaluators use `EMAIL-*` and `SIGNIN-*` control IDs and are not in `Config/controls.json` — they are heuristic IoC checks, not baseline controls.

## Project Structure

`TenantPosture/` contains `Invoke-TPAssessment.ps1` (single-tenant entry point), `Invoke-TPBatchAssessment.ps1` (multi-tenant batch entry point), `Invoke-TPBatchSignInTriage.ps1` (morning sweep across all GDAP clients), `TenantPosture.psm1` (module loader that dot-sources all subdirectories recursively), and `TenantPosture.psd1` (module manifest).

`Lib/` contains `Add-TPFinding.ps1` (state management: findings, raw data, coverage, Clear-TPState), `Connect-TPServices.ps1` (Graph + EXO + Teams + IPPSSession connection logic), and `Get-TPBaselineTier.ps1` (license detection and baseline compliance functions).

`Collectors/` contains one file per workload and is recursively loaded by the psm1. `AAD/` contains `Invoke-TPCollectAADInventory.ps1` (sets `AAD-Inventory`), `Invoke-TPCollectAADUsers.ps1` (sets `AAD-Users`), `Invoke-TPCollectAADAuthPolicies.ps1` (sets `AAD-AuthPolicies` and `AAD-CAPolicies`), `Invoke-TPCollectAADCAPolicies.ps1` (wrapper to AuthPolicies), `Invoke-TPCollectAADRoles.ps1` (sets `AAD-DirectoryRoles`, `AAD-PIMSchedules`, `AAD-IdentityGovernance`), `Invoke-TPCollectAADPIM.ps1` (wrapper to Roles), and `Invoke-TPCollectAADIdentityGovernance.ps1` (wrapper to Roles). `EXO/` contains `Invoke-TPCollectEXOMailboxConfig.ps1` (sets `EXO-MailboxConfig`) and `Invoke-TPCollectEXOConnectionFilter.ps1` (sets `EXO-ConnectionFilter`). `EXO/` also holds `Invoke-TPCollectDefender.ps1` (sets `Defender-Policies`; it reads Exchange Online cmdlets, so it lives beside the Exchange collectors, not in a `Defender/` folder). `DNS/` contains `Invoke-TPCollectDNSEmailRecords.ps1` (sets `DNS-domain` and `DNS-Summary`). `Teams/` contains `Invoke-TPCollectTeams.ps1` (sets `Teams`). `SharePoint/` contains `Invoke-TPCollectSharePoint.ps1` (sets `SharePoint`). `Intune/` contains `Invoke-TPCollectIntune.ps1` (sets `Intune`). `Purview/` contains `Invoke-TPCollectPurview.ps1` (sets `Purview`). `PowerPlatform/` contains `Invoke-TPCollectPowerPlatform.ps1` (sets `PowerPlatform`) and `Invoke-TPCollectCopilotStudio.ps1` (sets `CopilotStudio`, runs after it and reuses its environment list).

`Evaluators/` contains one file per workload, each function evaluating one control: `Test-TPControl-AAD.ps1` (41 functions), `Test-TPControlDefender.ps1` (18 functions), `Test-TPControlTeams.ps1` (17 functions), `Test-TPControlPurview.ps1` (15 functions), `Test-TPControlSharePoint.ps1` (13 functions), `Test-TPControlIntune.ps1` (13 functions), `Test-TPControlCopilot.ps1` (5 functions), `Test-TPControlPowerPlatform.ps1` (4 functions).

`Publishers/` contains 7 publishers: `Publish-TPAssessmentHTML.ps1` (interactive HTML report), `Publish-TPAssessmentSummary.ps1` (Markdown summary), `Publish-TPComplianceMatrix.ps1` (XLSX matrix), `Publish-TPDeltaReport.ps1` (run-over-run drift), `Publish-TPMonthlyReport.ps1`, `Publish-TPRemediationPlaybook.ps1`, and `Publish-TPRemediationScript.ps1`.

`Config/` contains `clients.json` (batch client list with TenantId, DelegatedOrg, and skip flags), `controls.json` (control definitions including `ControlId`, `Title`, `Severity`, `Workload`, `Category`, `CollectorDependency`, `EvaluatorFunction`, `Remediation`, `References`, and `LicenseRequirement` per control), `frameworks.json` (framework definitions for CIS / SCuBA / NIST / CMMC / ISO 27001 / SOC 2 / HIPAA / PCI DSS / DISA STIG / MITRE ATT&CK), `branding.psd1` (company name, contact, colors, hourly rate, fees), and `schema/controls.schema.json` (JSON Schema validating controls.json shape).

## Control Architecture

253 total controls across 9 workloads: Azure AD / Entra ID (AAD, 67), Exchange Online (EXO, 38), Defender for Office 365 (DEF, 28), Microsoft Teams (TMS, 28), SharePoint Online (SPO, 25), Purview / Compliance (PVW, 18), Microsoft Intune (INT, 18), Power Platform (PPL, 21), Email Auth DNS (DNS, 10). Severity breakdown: 13 Critical, 105 High, 94 Medium, 41 Low.

License-aware scoring is encoded per control via the `LicenseRequirement` string field in `controls.json` (e.g. "M365 Business Premium or Entra ID P1", "Defender for Office 365 P1", "E5 Compliance"). There are no separate per-tier baseline JSON files — the requirement lives on each control row.

**NIST SP 800-53 Rev 5 rollup.** All 253 controls carry a `References.NIST` citation, spanning 12 of the 20 800-53 families. `Lib/Get-TPNISTFamilyCoverage.ps1` rolls findings up by control family (AC, AU, IA, SC, SI, …) and by individual 800-53 control, using the same score formula and denominator rules as `Get-TPCoverageScore`. It parses the `NIST:` prefix off the flattened `FrameworkIds` string — never the bare identifier shape, which would also match CMMC's `IA.L2-3.5.3`. A finding citing controls in two families is counted in each, so family rows deliberately do not sum to the assessment total; every surface that renders them says so. The rollup appears in the HTML report (`id="nist-families"`), the Markdown summary, and a dedicated `NIST Families` sheet in the XLSX matrix. `TP.NISTFamily.Tests.ps1` pins both the parsing and the controls.json invariant that every control carries a parseable NIST citation — a control missing one vanishes from the family view, shrinking that family's denominator and inflating its coverage.

**Report framework selection.** `Invoke-TPAssessment.ps1 -Framework <NIST|CIS|SCuBA|CMMC|All>` decides which framework cards the HTML report shows. The entry point has NO default of its own: the active profile's `DefaultFramework` decides (`Config/profiles/nrg.psd1` says `NIST`; `nls.psd1` and the neutral `Config/branding.psd1` say `All`), pinned by `TP.FrameworkDefault.Tests.ps1`. The PUBLISHER default stays `@('CIS','SCuBA','NIST','CMMC')`, so direct callers are unaffected. **Profiles** (`TP_PROFILE` / `-Profile <name>` → `Config/profiles/<name>.psd1`, else `Config/branding.psd1` when no name is given, else neutral defaults; a name is `[a-z0-9-]`, never a path, judged in ONE place, `Resolve-TPProfilePath`, which both the module and the entry point use, and **a name that is not a profile is fatal, never a fallback**: the entry point exits 4 before anything else and the module refuses to import, naming the profiles that exist, because running another practice's defaults looks like any other run; loaded with `Import-PowerShellDataFile`, never executed; the entry point puts `TP_PROFILE` back after the import so a later run in the same console does not keep this run's practice, which is why the web server hands `-Profile` to the scan it launches; the declared `EdrStack` / `AwarenessStack` (`Get-TPProfileDeclaration`) and `MonitoringAddresses` are read from the LOADED profile (`$TPBrand`), never from a second read of `branding.psd1`, which is what dropped `-Profile nrg`'s declarations, and the report site and tenant onboarding read it the same way; `Get-TPStandards` lets the profile complete the shared default file but never an explicit `-Path`) hold the practice-specific data: company and contact, colors, `DefaultFramework`, `DmarcReportingAddresses` (which `Get-TPStandards` takes over the shared file's empty list), `EdrStack`, `AwarenessStack`, `MonitoringAddresses`, rates; `New-TPProfile` writes one from validated parameters (atomic, re-read with `Import-PowerShellDataFile` before the move, like the exception writer) and `Get-TPProfile` lists them. Nothing in a profile changes what is assessed or how it is scored. Narrowing is presentation only: `Publish-TPAssessmentHTML` scores all four regardless of `-Frameworks`, controls.json keeps every citation, and a test asserts no framework score moves when the report narrows. The `.fw-grid` column count is interpolated from the displayed set — hardcoding 4 renders a single card at quarter width. `Publish-TPNISTMatrix` also emits a **NIST-only HTML report** (alongside Markdown and XLSX) that mentions no other framework anywhere on the page; a test greps for CIS/SCuBA/CMMC/ISO/SOC/HIPAA/PCI/MITRE and fails on any leak.

**Standalone NIST matrix.** `Publish-TPNISTMatrix.ps1` emits a single-framework 800-53 Rev 5 deliverable (Markdown always, XLSX via openpyxl) behind the `-NISTMatrix` switch on `Invoke-TPAssessment.ps1`; `-AllFiles` implies it. Six sheets: Summary, Control Matrix (one row per 800-53 control x tool control), By Control, By Family, Physical & Device, Not Assessed. Official Rev 5 titles come from `Config/nist-800-53-catalog.json` via `Lib/Get-TPNISTControlCatalog.ps1` — note the Rev 4 -> Rev 5 renames the tool cites (AC-11 Device Lock, AT-2 Literacy Training and Awareness, AU-2 Event Logging, AU-4 Audit Log Storage Capacity, AC-6(9) Log Use of Privileged Functions, AC-16 Security and Privacy Attributes); `TP.NISTMatrix.Tests.ps1` pins them by name. **The matrix is strictly additive** — `Publish-TPComplianceMatrix` keeps all ten frameworks and no existing output changes; a test asserts publishing it does not move the CIS/SCuBA/CMMC scores. Every rollup table carries an Error column so Met + Partial + Gap + Error + N/A sums to Assessed; without it a reader who adds a row up comes short and has no way to tell whether the missing rows were passes or failures.

**NIST physical / media / device controls.** `Config/nist-physical.json` defines 31 800-53 controls covering endpoint posture, media, maintenance, personnel, and physical/environmental protection, each with the device aspect it covers and two or more implementation options. `Lib/Get-TPNISTPhysicalPosture.ps1` joins it against findings and renders in the HTML report (`id="nist-physical"`) and the Markdown summary. Each item declares a `Scope`: `Tenant` (10, fully evidenced by scored controls), `Hybrid` (7, partly evidenced, remainder off-tenant), or `Attested` (14, not observable from Microsoft 365 at all). **Nothing in this section is scored** — Tenant/Hybrid rows reflect findings already scored under their own control IDs, and `Attested` rows always report `Attestation required`, never a compliance state. That is the "advisory controls never claim compliance" rule applied to a whole section: the section exists so a reader cannot infer from a clean NIST family table that the physical families were assessed and passed. `TP.NISTPhysical.Tests.ps1` enforces the scope contracts (Tenant must cite evidence controls; Hybrid must cite both halves; Attested must name the off-tenant evidence and cite none), verifies every `EvidenceControls` ID exists in `controls.json`, and feeds the posture a findings set that satisfies every control in the tool to prove the attested rows still refuse to claim anything.

**Device guide (no scanning).** `Publishers/Publish-TPDeviceGuide.ps1` renders `Config/nist-physical.json` into a printable device/endpoint guide — 31 controls, 98 implementation options, Markdown plus self-contained HTML with print styling and no external assets. `New-TPDeviceGuide.ps1` is its standalone entry point and **connects to nothing**: no sign-in, no Graph, no EXO, no endpoint access, so the guide is usable before a tenant is attached. `-ResultsPath` optionally annotates it with a prior run's verdicts. Two invariants are statically enforced by `TP.DeviceGuide.Tests.ps1`: neither file may reference `Invoke-TPGraphRequest` / `Connect-MgGraph` / `Invoke-RestMethod` / `Get-TPRawData` etc., and supplying findings must not change the rendered options (a test diffs them with and without). Note `@($null).Count` is 1, not 0 — counting an omitted `-Findings` that way made the guide print "Assessment result: Not assessed" for controls nothing had assessed; strip nulls before counting.

**Device build standard.** `Config/device-baseline.json` holds 29 lifecycle requirements (procure / provision / harden / in-service / offboard), 25 mandatory, each with Why, How, `Nist` citations and `VerifiedBy` tool-control references. `Publishers/Publish-TPDeviceBaseline.ps1` renders it as a printable checklist plus detail; `New-TPDeviceGuide.ps1` emits it alongside the control reference as `<base>-baseline.md`/`.html`. Same no-network contract as the guide, statically enforced. `TP.DeviceBaseline.Tests.ps1` verifies every `VerifiedBy` exists in controls.json and every `Nist` entry resolves in the 800-53 catalog — both rot silently as the tool changes — and pins the mandatory set (DB-2.1 enrollment, DB-2.3 LAPS, DB-2.5 encryption, DB-3.2 EDR, DB-4.1 patching, DB-4.3 CA enforcement). Items with an empty `VerifiedBy` render "not checkable from the tenant" rather than letting a reader assume the assessment covers them.

**Endpoint device compliance (`DEV-*`).** `Device/Invoke-TPDeviceCompliance.ps1` runs ON the endpoint (RMM-deployed, SYSTEM) and writes a JSON result; `Collectors/Device/Invoke-TPCollectDeviceCompliance.ps1` ingests a folder of them behind `-DeviceResults`; `Evaluators/Test-TPControlDevice.ps1` aggregates to one finding per control with failing hostnames in `AffectedObjects`. 39 checks defined in `Config/device-controls.json` — deliberately NOT in controls.json, which is the 202 tenant controls and a stated product number. **The endpoint script is Windows PowerShell 5.1** and is the sole carve-out from the repo-wide `#Requires -Version 7` floor; `TP.Security.Tests.ps1` scopes that exception to the top-level `Device/` folder and asserts it earns it (no MSHTML/COM/Invoke-Expression/network). `TP.DeviceCompliance.Tests.ps1` additionally pins: no PS7-only syntax (checked over tokenizer output, not raw text — the file's own docs mention `??`), no module import, read-only apart from the single result write, and check IDs matching device-controls.json in both directions. **A result file is bound to a device, not a host name:** the collector keys on host name plus serial number, a host name seen with different serials is a `Conflict` the evaluator counts as neither pass nor fail (`Coverage.Conflicted`), and the schema is accepted at major version 1 under the `tp-` and the earlier `nrg-` name only. **The result is written only where SYSTEM owns it (2026-10-13 scan).** `ProgramData` lets a standard user create a folder there first and own it; a user-owned `ProgramData\TP` (or `NRG`, which an existing folder makes the default) is a result the user can edit after SYSTEM writes it, and a junction there sends SYSTEM's write wherever the user pointed it. Before the one `Set-Content`, the script refuses (exit 4, path and reason) any junction or symbolic link in the path, a folder or existing result file not owned by SYSTEM, Administrators or the running account (`Get-TrustedOwnerSids`), and a hard-linked result file; while elevated it gives the default folder a protected DACL (SYSTEM and Administrators write, Users read) BEFORE checking the file again, so nothing can be slipped in between check and write (`Initialize-OutputDirectory`, the script's one `Set-Acl`; the .NET `Directory` overloads that take a `DirectorySecurity` exist on .NET Framework only, and the Windows test job runs PowerShell 7). A `-OutputPath` folder is checked, never re-ACLed; a share's owner is not judged. The Windows CI job runs the endpoint suite, because the owner and DACL checks are Windows semantics. **Elevation honesty:** checks needing admin emit `NotAssessed`, which is excluded from the fleet denominator — never counted as a pass and never as a failure. **Event logs and audit policy (DEV-8.3–8.6):** sizes and full-log behavior come from `Get-WinEvent -ListLog` (what Windows applies, not the policy key); the verdicts are pure functions (`Get-EventLogSizeVerdict`, `Get-EventLogModeVerdict`) that the tests extract from the parsed script, and an unread log is NotAssessed, never assumed compliant. DEV-8.5 treats an absent `SCENoApplyLegacyAuditPolicy` as Microsoft's documented default (Enabled) and fails only an explicit 0. DEV-8.6 (Sysmon) is `Inventory`: an EDR collects the same telemetry, so absence is recorded, never failed. Note the `$rows = if (...) { @(...) } else { @() }` trap: an if-block yielding an empty array assigns `$null`, so build such variables in two statements.

**Improvement plan (`-ImprovementPlan`).** `Lib/Get-TPNISTImprovementPlan.ps1` turns the assessment from a position into a route: ordered steps against 800-53 Rev 5, each with the exact projected coverage after it, the families it moves, and what it will break. `Publishers/Publish-TPImprovementPlan.ps1` renders Markdown + self-contained HTML. **Single framework by design** — names NIST and nothing else, tested by the same `'\b' + escape($fw)` grep the NIST matrix uses (the `\b` matters: bare `CIS` matches "precisely" and "decision" case-insensitively and the test fails on its own prose). Only the parsed NIST control IDs are rendered, never raw `FrameworkIds`, which carries every other citation.

**Improvement-plan honesty rules.** The projected score is a number a client holds you to, so: cumulative figures are recomputed from counts at each step, never accumulated from rounded per-step deltas (a test re-derives every one independently); a license-blocked control gets NO projected score and no rank, because buying a license changes the denominator and licensed-but-unconfigured is still a gap; family movement is computed by REPLAYING the plan through `Get-TPNISTFamilyCoverage`, never by per-family arithmetic, which gets multi-family controls wrong; and `Ceiling.Note` states on page one that completing the plan is not 800-53 compliance. Two tracks: `Do now` requires a DOCUMENTED `none-visible`/`admin-review-workload`/`monitoring-integration` archetype — a control with no impact entry can never land there, since an undocumented impact is not evidence of no impact. Note `Test-TPLicenseRequirementMet` treats `Included*` requirements as met regardless of SKU data, so "actionable implies no LicenseRequirement" is the wrong invariant; the right one is "the helper confirms it met".

**Effort classes.** Each `operational-impact.json` archetype carries an `Effort`: `Single setting` / `Single setting, then ongoing` / `Policy change` / `Policy change, then tuning` / `Staged rollout` / `Discovery first` / `Project` / `License purchase` / `Review only`. Deliberately never an hour figure — an invented hour count is a promise the tool cannot keep and the first thing a client holds you to. A test pins the allowed set and greps for `\d+\s*(h|hr|hour|day|week)`.

**System Security Plan (`-SSP`, NIST 800-171 Rev 2 / CMMC Level 2).** `Lib/Get-TPSSPPosture.ps1` joins all 110 Rev 2 requirements from `Config/nist-800-171-r2.json` against findings; `Publishers/Publish-TPSSP.ps1` renders Markdown + self-contained HTML + XLSX. The requirement↔control join needs NO mapping table: a CMMC practice ID embeds its 800-171 number (`IA.L2-3.5.3` → `3.5.3`) and every control already carries a CMMC citation. `Get-TPNIST171RequirementIdsFromCmmc` matches the FULL practice-ID shape only — never bare `d.d.d`, which `Req 8.3` (PCI) would also match. Endpoint checks join through the `Nist171` array in `device-controls.json` (32 of 39 cited; 7 deliberately uncited rather than stretched). **41 of 110 requirements have automated evidence; 69 do not.**

**The SSP honesty rules — this is the one deliverable a client SIGNS.** A false `Implemented` here is a false statement in a compliance artifact handed to a C3PAO. So: a requirement with no mapped control is NEVER derived as implemented (`No automated evidence` / `Confidence: Attestation only`); a mapped control that produced no finding is `NotRun`, never a pass, and an `Error` state lands there too; a status asserted in the answers file gets `StatusSource = 'Attested'` and stays out of `Summary.ToolVerified`; `Confidence` distinguishes `Tool-verified` / `Partial evidence` / `No evidence collected` / `Attestation only`, because even an all-passing requirement is only evidenced to the extent M365 can see it. `TP.SSP.Tests.ps1` feeds a findings set satisfying EVERY control in the tool and asserts the 69 still claim nothing.

**Answers file.** `Config/ssp/<client-slug>.psd1`, loaded by `Lib/Get-TPSSPAnswers.ps1` via `Import-PowerShellDataFile` (data only, never executed — these get emailed between MSP and client). Shape: `System` / `Inherited` / `Requirements` with per-requirement `Status`, `Narrative`, `ResponsibleRole`, `Poam`, `NotApplicableReason`, `InheritedFrom`. `Config/ssp/example.psd1` is the template. **The entry point looks the file up by the CONNECTED domain (`$reportMetadata.TenantDomain`), not the `-TenantDomain` parameter** — under GDAP they differ and the wrong one attaches another client's narratives.

**HIPAA Security Rule readiness (`-HIPAA`).** `Config/hipaa-security-rule.json` (catalog `version`, `sourceSnapshot` = the eCFR issue date, `sourceRetrieved`) holds every standard and implementation specification of 45 CFR 164 Subpart C (63: 22 standards, 19 Required, 22 Addressable) with the regulation text, pinned by `TP.HipaaReadiness.Tests.ps1`; `Lib/Get-TPHipaaReadiness.ps1` joins it to findings through each control's existing `References.HIPAA` citation (a standard cited without its `(i)` means that standard; Privacy Rule citations, 164.5xx, are named and not mapped) and `Publishers/Publish-TPHipaaReadiness.ps1` renders Markdown + self-contained HTML. **Statuses are technical, never regulatory** (`Get-TPHipaaStatusNames`, module scope, the one copy of the strings): `Mapped technical checks satisfied` (every mapped check passed; a citation is not proof of full coverage and no coverage review is recorded), `Mapped checks satisfied, specifications open` (a standard is reviewed separately from its implementation specifications, and a parent citation never covers them; each standard carries its specifications' tally), `Technical check shortfall`, `Not assessed` (mapped checks produced no verdict, an Error, or a pass beside NotApplicable/NotRun), `Attestation required` (no check maps to it). `Mapped` and `EvidenceCollected` are separate counts: a mapping is not evidence until a check ran. Every finding's Detail is kept, Satisfied included, because it carries the qualifications. Items whose requirement is a document, process or organizational arrangement carry `TenantEvidence: None` with the reason, and a control citing one is listed as **cited, not counted**. Page one: not a risk analysis, not a compliance determination, Addressable is not optional; the regulation expressly requires documenting why one is not implemented (164.306(d)(3)), and recording every decision is labeled "Recommended practice", never stated as a requirement (164.316(b)); the catalog is the rule currently in effect, not the pending Security Rule NPRM (`ruleStatus`). A control's state in this view is judged over ALL its instances (Gap/Partial on any instance beats an Error on another, since an Error is no verdict; Satisfied only when every instance passed), deliberately not `Get-TPStateSeverityRank`'s Gap > Error > Partial, and every instance is kept in the evidence. `frameworks.json` labels the rule `2013 (as amended)` after the section source notes; the catalog's `amendments` also records the later eCFR version-history entries the notes do not cite, rather than claiming there are none.

**BOD 25-01 required configurations (`-BOD2501`).** `Config/bod-25-01-required.json` is CISA's Required Configurations list for Binding Operational Directive 25-01, Microsoft 365 rows only, taken by policy ID from the CISA page (`source`, `sourceRetrieved` 2026-10-27, `basis`): 56 policies, all SHALL, each with its released ScubaGear v2.0.0 statement and CISA's "Date Added / Modified" and "Due Date" values; the page names no ScubaGear version, so `scubaGear.version` is the release it was checked against (the v2.0.0 baselines carry the "BOD 25-01 Requirement" indicator on exactly these 56). Google Workspace rows (ScubaGoggles) are not encoded. Never derive the list from "every SHALL": when CISA changes the page, re-read it. `Lib/Get-TPBod2501View.ps1` joins each policy to the controls whose `References.SCuBA` cites it and to their relation in `scuba-alignment.json`; `Publishers/Publish-TPBod2501View.ps1` renders Markdown + self-contained HTML. A VIEW: no finding, no score. Statuses (`Get-TPBod2501StatusNames`, the one copy): `Tool-verified: met` (every Equivalent-relation control Satisfied), `Tool-verified: shortfall` (an Equivalent control Gap/Partial), `Partly checked` (only Partial-relation verdicts, or an Equivalent control without a verdict beside them; `NotChecked` names what the tool does not check), `Not assessed`, `Manual evidence required` (no control, or only Manual/Unsupported relations, listed as cited, not counted), `Product not assessed by this tool` (a product whose `AssessedByTool` is false). A met policy still names a Partial-relation control reporting a shortfall (`RelatedShortfalls`). A control's state over its instances follows the HIPAA view's order. With `-ScubaResultsPath` (read through `Read-TPScubaResults`, the report site's reader) ScubaGear's own result sits beside each policy and opposite directions are flagged `Results differ — review`, never resolved. Page one: a technical readiness view, not an attestation; the directive binds FCEB agencies; ScubaGear's report is what CISA expects. On an all-satisfied run 17 are met, 24 partly checked and 15 need manual evidence (pinned; a citation change moves these). `-AllFiles` implies it; it works with `-FromResults`; the report site does not render it. `TP.Bod2501.Tests.ps1` pins all of this.

**Operational impact (`Config/operational-impact.json`).** Answers "if we enable this, what breaks?" for all 230 controls — the question that decides whether a remediation is scheduled. 27 archetypes (`legacy-client-break`, `mail-delivery-risk`, `device-gate`, `admin-elevation-friction`, …) each with `Summary`/`Users`/`Admins`/`Watchouts`/`Reversible`; every control names one; `overrides` hold per-control differences and are kept SEPARATE from the archetype, not merged over it — merging printed near-duplicate blocks differing by one sentence. `Group-TPSSPImpact` collapses a requirement's actions to one block per archetype with the override attached as a short "X specifically" line. **A control with no entry returns `$null` and renders "Operational impact not documented" — never "no impact"**, which is the answer that gets a change approved without anyone checking.

License detection runs via `SubscribedSkus` in `Lib/Get-TPTenantLicenseProfile.ps1`, which returns a `HashSet` of LicenseRequirement strings the tenant satisfies. **Service plans are the authority, not part numbers**: `Config/license-service-plans.json` maps every requirement string (and, under `controls`, each control whose feature differs from others sharing its string — Customer Lockbox, Endpoint DLP, Audit Premium, DLP, labels, retention) to the plans that deliver it, sourced from Microsoft's service-plan reference and the Purview/Defender service descriptions. Always call `Test-TPLicenseRequirementMet ... -ControlId` so the per-control rule applies; never read `SuppressedLicenseRequirements` directly. Part-number reading is only the fallback when no plan data exists. Office 365 E3/E5 carry no Entra ID P1/P2 or Defender for Endpoint; Microsoft 365 E5's WINDEFATP includes Plan 1; Business Premium's Exchange Online Archiving covers holds and Defender for Business covers EDR. `TP.LicenseServicePlans.Tests.ps1` feeds Microsoft's published plan lists and fails if any non-`Included` requirement in controls.json has no rule — such a string is 'not licensed' on every tenant, which is how EXO-9.1 was never scored. `HasLicenseData` false means unknown: the report says licensing was not read and blocks nothing. `Test-TPLicenseRequirementMet` answers per-control whether the tenant has the licenses needed. **Note `O365_BUSINESS_PREMIUM` is Microsoft 365 Business STANDARD** (Microsoft's licensing reference) — it was matched as Business Premium, labeling every Business Standard tenant Business Premium; `SPB` and the two no-Teams variants are Business Premium, and E3/E5 (Microsoft 365 or Office 365, incl. government) satisfy "M365 Business Premium or E3+".

## Data Flow

`Connect-TPServices` establishes Graph (24 scopes) plus EXO, Teams (optional), and IPPSSession (optional). Collectors run first and populate module-scope raw data using `Set-TPRawData` with a key per workload. Each result object has `CollectorId`, `CollectedAt`, `Success`, and `Data`. Evaluators read raw data using `Get-TPRawData` and write findings using `Add-TPFinding` with states of `Satisfied`, `Gap`, `Partial`, `NotApplicable`, or `Error`. Publishers consume findings via `Get-TPFindings`, calculate the license-aware score via `Get-TPBaselineTier`, and produce the HTML report and JSON export.

Raw data keys and their collectors: `AAD-Inventory` set by `Invoke-TPCollectAADInventory`; `AAD-Users` set by `Invoke-TPCollectAADUsers`; `AAD-AuthPolicies` set by `Invoke-TPCollectAADAuthPolicies`; `AAD-CAPolicies` set by `Invoke-TPCollectAADAuthPolicies` via wrapper; `AAD-DirectoryRoles`, `AAD-PIMSchedules`, `AAD-IdentityGovernance` all set by `Invoke-TPCollectAADRoles` via wrappers; `EXO-MailboxConfig` set by `Invoke-TPCollectEXOMailboxConfig`; `EXO-ConnectionFilter` set by `Invoke-TPCollectEXOConnectionFilter`; `Defender-Policies` set by `Invoke-TPCollectDefender`; `DNS-domain` and `DNS-Summary` set by `Invoke-TPCollectDNSEmailRecords`; `Teams` set by `Invoke-TPCollectTeams`; `SharePoint` set by `Invoke-TPCollectSharePoint`; `Intune` set by `Invoke-TPCollectIntune`; `Purview` set by `Invoke-TPCollectPurview`; `PowerPlatform` set by `Invoke-TPCollectPowerPlatform`.

## Module State

All state is module-scope and cleared between batch clients by `Clear-TPState`, which resets four variables: `TPFindings` (List of hashtable), `TPRawData` (Dictionary), `TPCoverage` (Dictionary), and `TPExceptions` (List of hashtable). `Clear-TPState` must be called between batch clients or raw data from one client bleeds into the next client's evaluation.

## Coding Standards

Every script file requires a header block with `#Requires -Version 7.0`, the filename, NRG Technology Services / NextLayerSec LLC, Author: Matthew Levorson, a one-line purpose statement, the data keys set or consumed, and the Graph scopes or cmdlets required.

All functions use `[CmdletBinding()]`. All data structures that get serialized use `[ordered]` hashtables. All external API calls use `ErrorAction Stop` and are wrapped in `try/catch` with `Register-TPException`. `Write-Host` is never used in collectors or evaluators — use `Write-Verbose` only. No hardcoded credentials, tenant IDs, or domain names in code. Exit codes are 0 for success, 1 for auth failure, 2 for no findings, 3 for partial collection, 4 for fatal error.

Every collector must initialize a result object with `CollectorId`, `CollectedAt`, `Success` set to `false`, and a `Data` block; execute API calls inside `try/catch`; set `Success` to `true` on completion; call `Set-TPRawData`; and call `Register-TPCoverage`.

Every evaluator must guard against missing data as its first action. If `Get-TPRawData` returns null or `Success` is false, register `NotApplicable` and return immediately. Never allow a null reference to propagate into evaluation logic. `Add-TPFinding` accepts `ControlId`, `State`, `Category`, `Title`, `Severity`, `Detail`, `FrameworkIds`, `CurrentValue`, `RequiredValue`, `Remediation` (NOT `RemediationSteps` — that parameter does not exist), and `AffectedObjects` (structured per-finding objects, e.g. recipient warn-lists or flagged inbox rules).

**Empty is not clean — `SectionStatus`.** Collectors that run several independent queries wrap each in its own `try/catch` so one failure does not abort the rest, then set `Success = $true` regardless. That makes an EMPTY list ambiguous: it can mean "queried, found nothing" (compliant) or "the query failed" (unknown), and `Success` cannot tell them apart. Any collector with independent sub-queries MUST therefore publish `Data.SectionStatus`, a map of section name to `NotRun` / `Collected` / `Failed`, and any evaluator about to conclude `Satisfied` from an empty list MUST consult it first and report `NotApplicable` when the section did not complete. Reading an empty list as compliance produced false clean bills of health on the BEC exfiltration, persistence and tenant-takeover controls — the highest-consequence class of bug this tool can have. Collectors implementing this today: `EXO-Inventory`, `AAD-DirectoryRoles`, `AAD-Inventory`, `Purview`, `PowerPlatform`. Absent `SectionStatus` is treated as collected so replayed older result JSON keeps its previous behavior.

**A section that was not collected says why (`Get-TPSectionNotCollectedDetail`).** A collector that fails a section records the reason beside the status (`Data.SectionErrors.<Section>`; the Purview collector does, both for a cmdlet absent from the Security & Compliance session, with the role hint, and for a thrown read), and a finding built from the "X was not collected; not assessed." boilerplate goes through the helper, which keeps that sentence as the prefix (the scope classifier, the baseline reason contract and the tests key on it) and appends "Reason recorded by the collector: ...", falling back to the registered exception (`-CollectorSource`) on a live run. A reason never changes the state, and every such finding carries `-FrameworkIds $cit`, because an uncited NotApplicable vanishes from the NIST rollup. The 2026-10-14 run put the missing Purview role in the Exceptions array and nothing in the deliverable; a reason the collector already wrote down belongs in the finding that depends on it. Other collectors do not record section reasons yet; the helper returns the plain sentence for them.

**Empty is not the only false clean — parse the shape the API actually returns.** `SectionStatus` catches "the query failed"; it cannot catch "the query succeeded and we read the answer wrong". `Lib/Get-TPRecipientClass.ps1` exists because the external-recipient test split on `@` and required exactly two parts, while Exchange returns `"user@dom.tld" [SMTP:user@dom.tld]` — the address **twice**, three parts, so every genuine external rule recipient was classified internal and EXO-7.2 reported clean on tenants with live exfil rules. Two rules follow. First, **classification is tri-state** (`External`/`Internal`/`Unresolved`, plus `Orphaned`): a boolean collapses "known internal" and "could not tell" into the safe-looking answer, so a legacy `[EX:/o=…]` DN is resolved through `Get-Recipient` and reports `Unresolved` when that fails, which the evaluator renders `NotApplicable`. Note `Unresolved` is a truthy string — callers MUST compare `-eq 'External'`, never use the value as a boolean, and a test pins that. **"Could not ask" and "asked, holds nothing" are different answers (`Lib/Resolve-TPExoRecipient.ps1`).** `Unresolved` used to cover both, so one deleted mailbox in an old rule left EXO-7.2 "not assessed" on every run of a tenant, for months. The resolver's contract has three answers: an object; `$null` ONLY when the directory answered (for a legacy DN: nothing by LegacyExchangeDN through `-Identity` AND nothing by X500 proxy address through `-Filter "EmailAddresses -eq 'X500:…'"`, the two attributes Exchange routes a legacy DN by, so mail to it is not delivered); a throw when it could not be asked (no session, throttling, a refused identifier, or any error that is not Exchange's `ManagementObjectNotFoundException`, recognized by type name in the error id, exception chain or `|Type|Message` text, **or by Exchange's own not-found sentence** "The operation couldn't be performed because object '…' couldn't be found on '…'" with either apostrophe, because the REST-backed cmdlets of module 3.x render the server error as `||Message` with the type blank and the 2026-10-15 live run left two orphaned rules "not assessed" that way; never by the `ObjectNotFound` category, which a missing command also reports). The classifier turns the `$null` answer into `Orphaned` for the `[EX:` form only (a display name is not an identifier), the collector stores `OrphanedRecipients`/`IsOrphaned` and records every throw as an `EXO-RecipientLookup` exception, and EXO-7.2 scores an orphaned-only rule as a **Gap at Medium severity** (owner's 2026-09-15 decision: a forwarding rule that is not delivering is a gap pending a decision on the feed) whose Detail states what was established and what was not. A rule with an unresolved recipient is still a blind spot and the control is still not assessed; `TP.ExchangeTruth.Tests.ps1` drives the real collector with Get-Recipient stand-ins answering as the Exchange Online module does, so `IsOrphaned` is produced by the real path, never by a fixture. Second, **fixtures must carry raw API shapes, not derived fields**: every fixture fed the evaluators a pre-computed `IsExternal` and so never exercised the parser, which is why it shipped broken and stayed broken. A fixture of `attacker@evil.tld` passes against the broken parser.

**`signInActivity` is a licensed property.** Graph refuses a `$select` that names it on a tenant without Microsoft Entra ID P1 or P2 ("Neither tenant is B2C or tenant doesn't have premium license"), and the refusal takes the whole user query with it. The inventory collector re-reads the guest and member lists without the property on that error and records `SignInActivityLicensed = $false`; AAD-12.2 and AAD-12.3 then report a licensing upgrade opportunity (never a collection failure, never a pass), and the guest list stays available to the controls that only count guests. The same error is recognized for the MFA registration report (`MFARegistrationFailure = 'PremiumLicenseRequired'`); any other failure of either read still fails its section. The shared paging helper EMITS its rows, never `,$rows`: an array returned as one object through a second scriptblock (the retry wrapper's `try`) arrives at the caller's `@()` nested, one element holding the whole list, so an empty list became one empty-array row whose `.displayName` throws under StrictMode and a full list became one row, which a one-row fixture cannot tell from a list of one; the tests feed two rows and pin the count and names, and the smoke run's all-empty shape has its own case.

**Microsoft APIs OMIT optional properties — they do not null them.** Graph does not return `signInActivity` at all for a user who never signed in or last signed in before April 2020 (documented on the user resource type). Under StrictMode a nested read on an absent intermediate THROWS before `??` applies, so `$_.signInActivity.lastSignInDateTime ?? ''` failed on exactly the stale and never-signed-in accounts the guest and stale-account collectors exist to find — one such guest, which nearly every tenant has, failed the whole section, and those controls reported `NotApplicable` on every real run. Silently non-functional is the failure mode here, not falsely clean, and nothing surfaces it: `NotApplicable` is excluded from the denominator, so the score looks fine. Every nested read of API data goes through `Get-TPNestedProperty`, enforced statically by `TP.ExternalShapes.Tests.ps1`. A null intermediate throws identically, so there is no "safe" shape — the guard is absolute. Parse timestamps with `[datetime]::TryParse(..., [cultureinfo]::InvariantCulture, RoundtripKind, [ref]$x)`, never a bare `[datetime]` cast: this runs on whatever workstation the MSP uses.

**`Test-TPSectionCollected`'s fallback reads a present-but-empty array as collected.** That is deliberate (replayed older JSON keeps its behaviour), but it means any collector that PRE-INITIALISES its sections to `@()` MUST publish `SectionStatus` — presence alone cannot distinguish "queried, none found" from "the query failed". `AAD-PIMSchedules` lacked it, and AAD-3.2 read the resulting empty `EligibleSchedules` as "no PIM adoption" and scored `Partial` (0.5 credit) on a privilege-escalation control. The same evaluator would also emit **`Satisfied`** — "No permanent privileged role assignments" — when `AAD-DirectoryRoles` was missing entirely, because `$permanentPriv` merely stayed empty; a verdict about role assignments requires the role data, so the evaluator now returns `NotApplicable` without it.

**A failed DNS lookup is not an absent record.** `Resolve-TPDns` returned `@()` for any DoH response lacking an `Answer`, never reading `Status` — but Cloudflare returns SERVFAIL as HTTP 200 with `Status: 2` and no `Answer`, so a failing resolver was indistinguishable from NXDOMAIN, and the bare `return` also short-circuited the Google fallback and the `Resolve-DnsName` fallback beneath it. One transient SERVFAIL therefore produced a confident "no DMARC record", and the DNS evaluators score an absent record as a **Gap** — telling a client their email authentication is missing when it is not. Only Status `0` (NoError/NODATA) and `3` (NXDOMAIN) are authoritative "no record"; every other status falls through to the next provider. The optional `-Outcome ([ref]$x)` returns `Answered` / `NoRecord` / `LookupFailed`; the collector records it per record type in `Data.Domains.<domain>.LookupStatus`, and `Add-TPDnsLookupFailedFinding` (one helper, not seven pasted guards) gates the seven evaluators that score absence (SPF, DKIM, DMARC, MTA-STS, TLS-RPT, DNSSEC, CAA) so a failed lookup reports `NotApplicable` **with the control's citations** — an uncited `NotApplicable` is dropped by the 800-53 family rollup as unmapped and never reaches the NIST matrix's "Not Assessed" sheet. Four rules from review of the first version. A DoH body with **no readable `Status`** (a proxy block page, a captive portal, a JSON error object — all HTTP 200) is a failure, not an answer; the first version read it as `NoRecord` and never asked the next provider. The `Resolve-DnsName` fallback reports NXDOMAIN and NODATA by **throwing**, so the catch reads the Win32 code — 9003 `DNS_ERROR_RCODE_NAME_ERROR` and 9501 `DNS_INFO_NO_RECORDS` are `NoRecord`; mapping every throw to `LookupFailed` meant that on a workstation where DoH is blocked no DNS control could ever emit a Gap. NODATA has a **second shape**: the cmdlet returns every record on the wire, so a NODATA answer can arrive as only the zone's SOA in the **Authority** section (RFC 2308 §3), and stringifying that row made a DS lookup on an unsigned zone report `Answered` — DNS-1.6 scored Satisfied. The fallback keeps only Answer-section rows of the requested type, as the DoH path already does. And `-as [int]` is far too generous for `Status`: `$null`, `''` and `$false` all cast to `0` and `2.6` rounds to `3`, so `Status` is accepted only as a whole number or a digit string, and an `XmlDocument` body (a block page that happened to be well-formed) is rejected outright because it exposes its root element as a property. The fallback renders every row in the **same text shape the DoH path returns** (`FLAGS TAG "VALUE"` for CAA, `PREF exchange` for MX, the four DS fields) — `[string]$_` on a DnsClient record gives `@{Section=Answer; Type=CAA; …}`, which the collector's CAA parse could never match, so a present CAA record scored DNS-2.2 as a false Gap on a DoH-blocked workstation; a row the fallback cannot render is a `LookupFailed`, never an `Answered` with unusable data. Win32 9701 `DNS_ERROR_RECORD_DOES_NOT_EXIST` joins 9003/9501 as an absence code. Answer rows are read through `PSObject.Properties` and a row lacking `type`/`data` is skipped rather than failing the provider. Note the DKIM control deliberately checks the customer's selector CNAMEs, not the targets: Microsoft 365 rotates DKIM keys and the inactive selector's target is routinely NXDOMAIN, so a dangling target is not a finding. DNS-2.1 states each domain's last DKIM rotation date (`KeyCreationTime`, UTC) and, as an unscored cross-check, reads the published key behind each selector CNAME for its `n=` creation timestamp and key size (`DKIM.KeyRecords`); an absent target is recorded as `NoRecord`, never an error, and never touches `LookupStatus`. 365 days is the tool's rotation cadence, not a NIST figure (SP 800-57 gives signing keys one to three years). `LookupStatus` is **initialised to `LookupFailed`** for every gated key and only improved by a completed lookup, because the absent-key-means-collected replay rule would otherwise let a throw between the resolver and the assignment fail the gate open on a live run. And `Resolve-TPDns` never throws, so `-Reason ([ref]$why)` carries which providers failed and why into `$d.Errors` and the Exceptions array — without it the finding said "every resolver failed" and nothing in the results JSON said how. Coverage for `DNS-EmailRecords` is `Partial` when any lookup failed and `Failed` when all did, never `Collected` on a run in which nothing resolved — and `Failed` must be reachable on a ONE-domain tenant: the entry list is built as `@(if (...) { $map.Values } else { $map })` with the `@()` around the whole `if`, because an if-statement unrolls the array it yields and the lone hashtable's `.Count` is its key count (the `$rows = if (...)` trap again). The collector validates every outcome before writing it — only `Answered`/`NoRecord` may improve on the `LookupFailed` default, since `Test-TPDnsLookupSucceeded` reads a blank as collected — and every per-record `catch` records the throw in `Errors` and the Exceptions array; an empty `catch { }` beside a coverage note that says "see Exceptions" is a lie. `TP.DnsCollector.Tests.ps1` pins all of this by injecting a mock resolver into module scope (`Set-Item function:script:` via `& $module {}`), which is the only way to intercept a call made from inside the module. Absent `LookupStatus` counts as collected, so replayed older JSON keeps its behaviour. Pinned in both directions by `TP.DnsResolution.Tests.ps1` for all seven controls: `LookupFailed` must not score, `NoRecord` must still be a Gap, and the replay fixture omits the key rather than passing an empty map. **A probe target is resolved by the tool's own resolvers when the workstation's cannot (2026-10-15 live run).** `Test-TPSafeProbeTarget` resolved `mta-sts.<domain>`, the MX host and `autodiscover.<domain>` through the workstation's resolver only (`Resolve-TPWorkstationHostAddresses`, a function so a test can stand in for the operating system); on the operator's network both tenant domains' MTA-STS hosts, CNAMEs to a GitHub Pages host, returned "No such host is known" on every run since 2026-09-25 while the `_mta-sts` TXT records resolved over DoH, so DNS-1.4 was "not assessed" on two domains whose policies read `mode: enforce`. The guard now falls back to `Resolve-TPPublicHostAddresses` (A and AAAA through `Resolve-TPDns`, the chain every record lookup uses), validates every address with `Test-TPGloballyRoutableAddress` exactly as before and pins the fetch to it, returns `ResolvedBy` and the workstation's error, and the collector records `PolicyHostResolvedBy` / `WorkstationResolverError` beside the policy and a line in `Errors`; the DNS-1.4 pass then says the host was resolved through public DNS and the assessor's network is what could not (CurrentValue too, since the HTML report renders a Satisfied finding's CurrentValue only). An authoritative no-record from public DNS is still the Gap (`PolicyHostMissing`, read from the guard's `PublicDnsOutcome`), a public lookup that did not complete is still not assessed with both resolvers named, and an answer whose rows are not addresses is a failed lookup, never a missing host. `TP.DnsCollectorShape.Tests.ps1` drives the real guard with the workstation lookup and the bounded fetch stood in for.

**Network answers are parsed with bounds (`Lib/Test-TPPublicAddress.ps1`).** A connection target passes `Test-TPGloballyRoutableAddress`, a positive rule applied after unwrapping IPv4-mapped, NAT64 and 6to4 forms, and the socket is created for that address's family; never extend a deny-list instead. An HTTPS body from a tenant-chosen host (MTA-STS, crt.sh) is read with `Get-TPBoundedHttpText`: whole-transfer timeout, no redirect, byte cap. DoH TXT data goes through `ConvertFrom-TPDnsTxtData`, linear, and an unterminated quote fails the provider. Numbers in DNS answers are ASCII `TryParse`, one bad row skipped. `TP.NetworkParsers.Tests.ps1` runs a local TLS server to prove the redirect, cap and timeout. **The DNS suites stub the bounded reader itself.** The crt.sh and MTA-STS reads go through `Get-TPBoundedHttpText`, not `Invoke-WebRequest`, so a suite that stubs only the cmdlet still reaches crt.sh on every collector run and takes as long as crt.sh takes (the three DNS suites did, 50 seconds locally and a Pester job past its 30-minute ceiling on main on 2026-10-15); `TP.DnsCollector`, `TP.DkimRotation` and `TP.DnsCollectorShape` inject a `Get-TPBoundedHttpText` that throws, and a test that needs a body answers only its own URL.

**An unassessed control is invisible unless something names it — `Get-TPAssessmentScope`.** `NotApplicable` is excluded from the compliance denominator, which is correct, but it means a control that silently stops producing a verdict makes the score go **UP**. That is the shape of every high-consequence bug this tool has had: the omitted `signInActivity` property, the missing `AAD-PIMSchedules` SectionStatus, the DNS lookup read as an absent record. In each case the score looked fine and nothing in the deliverable said the control had gone quiet. `Lib/Get-TPAssessmentScope.ps1` is the surface that says it, rendered as the **Assessment Scope and Limitations** section in the HTML report (`id="scope"`, directly under the score) and the Markdown summary. It sorts every control in `controls.json` into exactly one bucket — scored, `LicenceBlocked` (benign, already priced under Upgrade Unlocks), `CollectionIncomplete` (**the dangerous one**: the control could have been assessed and was not), `NoProgrammaticCheck` (advisory, honest by design but it must be visible rather than implied), or `NoResult` (**worse still**: the control emitted nothing at all, so it is absent from the report entirely) — and it is the only place that computes the set difference `controls.json − findings`. Three rules. It is a **view, not a verdict**: it emits no findings and moves no score, and `TP.AssessmentScope.Tests.ps1` pins both. The buckets must **sum to the unscored count** with no control in two of them, because a control that is unscored and in no bucket is exactly the failure mode the section exists to end. And the limitations text **never reassures** — a test greps it for "is compliant", "no issues found" and friends. For a control with several instance findings (DNS per domain, the named-object evaluators) the **worst** state wins: assessed on one domain and not another is "partly", and partly is the honest answer.

**Absence of evidence is never evidence — the classifier's ordering rule.** The first version of `Get-TPAssessmentScope` inverted `Test-TPLicenseRequirementMet`, which returns `$false` when there is **no SKU data at all** (deliberately, so Upgrade Unlocks over-reports an upgrade need rather than hiding one). Inverted, "we cannot tell how this tenant is licensed" became "licence gated, benign" — so on any run where the licence profile did not populate, including every `-FromResults` republish, controls whose own `Detail` read *"EXO data not collected"* were filed as benign. The honesty section had the dishonesty bug. Every signal is therefore consulted only when **positively present**, strongest first: (1) the evaluator's own `requires manual verification` marker, which is authoritative about itself; (2) **hard evidence** — the control's `CollectorDependency` raw-data key is absent or its `Success` is false, the same signal the evaluator gated on, used **only when raw data is actually populated**, since an empty map means replay, not universal failure; (3) licence, only on the evaluators' explicit `upgrade opportunity` marker or a profile carrying real SKU data; (4) last and weakest, the evaluator's prose. The prose patterns are **derived empirically** — every evaluator is run against empty state and the distinct `Detail` strings collected — never invented to match the regex, which is how *"Teams collector did not run."* and *"Neither AAD-Users nor AAD-AuthPolicies collector produced data."* went unmatched and were reported as "no automated test". `TP.AssessmentScope.Tests.ps1` drives the real 179 evaluators with no data and asserts every resulting `NotApplicable` lands in collection-failed or self-declared-advisory and that **nothing** is called licence gated. `-Quick` deliberately drops evaluators, so their controls get their own `NotEvaluatedThisMode` bucket rather than `NoResult`'s "treat this as a tool fault". `-FromResults` restores `Coverage` and `RawData` into module state before publishing, because a republish that silently loses them looks cleaner than the run it reprints.

**Application permissions are the half of app risk the delegated table cannot see — `AAD-15.1` / `AAD-15.2`.** AAD-12.4 reads `oauth2PermissionGrants` with consentType `AllPrincipals`. That is the **delegated** consent table: an app acting as a signed-in user. An app-only grant is an **`appRoleAssignment`** and does not appear there at all, so a malicious application permission returns ZERO rows from the endpoint AAD-12.4 queries and the report says the tenant is clean. `Collectors/AAD/Invoke-TPCollectAADAppPermissions.ps1` reads the other table. The distinction is the whole point: an application permission is exercised with **no signed-in user**, so no MFA prompt fires and the activity does not look like a person in the sign-in logs. Conditional Access can reach it only through a workload-identity policy, which covers eligible single-tenant service principals and not multitenant apps or managed identities, so the findings say that instead of "no Conditional Access applies". `Mail.ReadWrite` app-only reads every mailbox; `RoleManagement.ReadWrite.Directory` makes the app Global Administrator; `Domain.ReadWrite.All` adds a federated domain and forges tokens for anyone. Collection asks each high-value RESOURCE who holds a role on it (`/servicePrincipals/{id}/appRoleAssignedTo` for Graph, Exchange and SharePoint) rather than asking every principal what it holds — three paged queries instead of hundreds. **No new Graph scope**: `Application.Read.All`, `Directory.Read.All` and `Organization.Read.All` are already requested, so this needs no re-consent in any client tenant, and a test asserts that. Four rules. `Config/app-permissions-risk.json` holds the judgement as reviewable data, tier 1 (takeover) and tier 2 (mass data access), each entry carrying the reason it is rated; a permission in neither tier is **collected and reported but not scored**, because absence from the catalog means unrated, never safe. Microsoft first-party apps legitimately hold these, so they are excluded from the VERDICT and their count is **stated in the detail** — set aside, never silently dropped — while an app whose owner cannot be determined is scored, not waved through. `SectionStatus` is per resource and **every** watched resource must read `Collected` before either control will reach a verdict: Exchange is where `full_access_as_app` lives, so scoring Graph alone and calling it clean would miss the worst grant in the product. And `@odata.nextLink` must be read with `Get-TPObjectField`, **never `Get-TPNestedProperty`**, which splits its path on `.` and resolves `@odata` → `nextLink`, returning the default so paging silently stops after page one and a partial list is reported as a full enumeration.

**Third-party EDR (`-ThirdPartyEDR`, clients.json `ThirdPartyEDR`).** Microsoft 365 cannot see a non-Microsoft EDR such as Cortex XDR, so its clients read as a Gap on every Defender endpoint check. `Lib/Set-TPThirdPartyEdr.ps1` runs after evaluation (and on `-FromResults`) and rewrites INT-1.5, INT-2.1, INT-2.2 and DEV-2.1–2.4/2.8 to `NotApplicable` with a `Third-party EDR declared:` detail: declared by the assessor, NOT verified, out of the score, naming what to confirm in the vendor console and keeping the original result. A check that PASSED keeps its verdict, because that is evidence. The declaration explains ABSENT Defender configuration, never an assigned policy read as falling short: an INT-2.2 `Shortfall:` keeps its verdict with an appended `Not excused by the third-party EDR declaration` note (idempotent). `Get-TPAssessmentScope` files these in their own `ThirdPartyAttested` bucket, keyed on that detail prefix; change both together. **Third-party security awareness (`-ThirdPartyAwareness`, clients.json `ThirdPartyAwareness`, branding.psd1 `AwarenessStack`)** is the same contract for phishing simulation (e.g. KnowBe4): `Lib/Set-TPThirdPartyAwareness.ps1` rewrites a non-passing DEF-4.6 with the `Third-party security awareness declared:` prefix, runs before license gating, and on `-FromResults` unwraps a license-gated finding so the `upgrade opportunity` marker never survives. Same `ThirdPartyAttested` bucket, keyed on either prefix. A NotApplicable matching no signal is `NotApplicableToTenant` (checked, does not apply, reason stated) — never `NoProgrammaticCheck`, which is only for the explicit advisory markers.

**The maturity label is provisional when evidence is incomplete (`Lib/Get-TPMaturityTier.ps1`).** The tier and score are computed over the scored controls (Error and unknown states are outside the denominator by design: a tool failure is not a gap), but excluding a finding does not make it a pass, so whenever any finding produced no verdict, or no control was scored, `EvidenceComplete` is `$false`, `Label` reads `<tier> (provisional: evidence incomplete)`, `ObservedLabel` keeps the bare tier name and `Qualification` carries the counts. No threshold waives it. The console prints the qualification under the tier line; a `-FailOn*` gate on incomplete evidence warns and keeps its exit code. `TP.MaturityTier.Tests.ps1` pins it, including that 50 passes beside 50 errors is never an unqualified "Optimizing".

**One worst-state order.** `Get-TPStateSeverityRank` (Gap > Error > Partial > NotApplicable > Satisfied) is used by the score (`Get-TPScoringFindings`), the scope section and the SSP; a pass needs every instance to pass. Anything counting fixes or projecting a score (roadmap, improvement plan, severity pills) iterates `Get-TPScoringFindings`, one finding per control — never raw findings, which carry one per DNS domain. The SSP derives `Implemented` only when every mapped control is Satisfied; any NotApplicable/NotRun beside passes is `Not assessed` with `Partial evidence`.

**Graph consent (`Lib/Get-TPGraphConsent.ps1`).** `Connect-TPServices` records the token's granted scopes as raw data `Graph-Consent`. AAD-8.2, AAD-11.3 and DEF-4.6 name the missing consent only when that list was actually read; no record or an empty list keeps the generic message. `Grant-TPGraphConsent.ps1` (repo root, sign-in only) performs the one-time consent. The delegated scope list lives in one function, `Get-TPGraphScopeList`; the batch runner keeps a copy because it signs in before the module loads, and `TP.TenantPinning.Tests.ps1` pins the two equal.

**Conditional Access view (`Lib/Get-TPConditionalAccessView.ps1`).** A VIEW, like `Get-TPAssessmentScope`: it emits no findings, moves no score, and is not exported (tests call it in module scope). Owner's ask: show which CA policies are in audit (report-only) mode, and what CA "should be in place for future" — without judging a policy scoped to one app (the owner's own LinkedIn example) against a template it was never meant to satisfy. Every policy in `AAD-CAPolicies` gets its true state — `enabled` **On**, `enabledForReportingButNotEnforced` **Report-only (audit)**, `disabled` **Off**, anything else **Unknown state (never Off)** — and a plain-English description built only from the fields the collector stores. It is compared against `Config/conditional-access-baseline.json`, 11 of Microsoft's own documented Conditional Access templates (block legacy authentication, MFA for all users / admins / Azure management, phishing-resistant admin MFA, block device code flow, sign-in and user risk, device compliance and its compliant-or-MFA alternative, no persistent browser session), each cited to its Microsoft Learn page. Matching is conservative and reuses the SCORED evaluators' own helpers unchanged (`Get-TPCAGrantAlternatives`, `Test-TPCAAllUsers`, `Test-TPCAAllApps`, `Test-TPAuthStrengthPhishResistant` from `Evaluators/Test-TPControl-AAD.ps1`) so the view never disagrees with the score about what a grant requires: **Enforced** only from a policy that is On, targets all resources with no exclusion (`Test-TPCAAllApps`, checked BEFORE anything else — the bug this caught: a policy scoped to one app matched "require MFA for admins" because that template's eligibility check never looked at resources), and targets all users (or, for the two admin templates, every role this tenant's own `AAD-DirectoryRoles` catalog marks `IsPriv` — never Microsoft's specific 14-role list, which the tool cannot verify against an unnamed tenant); a narrower, report-only, or weaker policy is **Similar** ("Partly in place"); a policy matching nothing is **Custom** and is never judged. `block-legacy-auth` and `block-device-code` require the grant to actually **block** — Microsoft documents that MFA does not stop either attack (device code: attackers relay the MFA prompt; the same rule AAD-11.1's evaluator applies), so an MFA-only policy on either is `NoMatch`, not a partial credit. Baseline status precedence (Security Defaults, then a real Enforced/Similar match, then licensing) matters: the second bug this caught was every row reading "needs a license" even when a policy was actively enforcing it, because licensing was checked first and a `$null` license profile (not read) was treated as a confirmed absence — `Test-TPLicenseRequirementMet` returning `$false` for unknown licensing is correct for gating a real control, but a firm "NotLicensed" claim needs POSITIVE evidence (a profile with `HasLicenseData = $true`; `Get-TPTenantLicenseProfile` returns a profile object even when no SKU was read), so an unread profile renders **Missing** with a "not read" note, never **NotLicensed**. Security Defaults (`Get-TPSecurityDefaultsState`) makes every CA template `CoveredBySecurityDefaults` (the four it documents) or `Missing` — never Enforced from a policy that cannot be on; no CA policy On and Security Defaults not read renders **NotRead**. `TP.ConditionalAccessView.Tests.ps1` pins both bugs plus the catalog's own integrity (every `SourceUrl` a real Microsoft Learn link, every `LicenseRequirement` a key `license-service-plans.json` understands).

**User consent has four Microsoft built-ins, not two (AAD-6.2).** `ManagePermissionGrantsForSelf.microsoft-user-default-legacy` (anything; Gap), `-low` (low-impact from verified publishers; verified), `-recommended` (the Microsoft-managed policy and the default for new tenants: any delegated permission from any publisher except the file, site, mail, calendar, chat, online-meeting, contacts, tasks, people and legacy mail-protocol scopes Microsoft lists; a **Partial**, verified for what it blocks and a shortfall for what it still allows) and `-allow-consent-apps` (named mail clients for mail scopes; a companion, named and never called custom). The invariants: no finding → NotVerified; a collector that did not succeed, or coverage Failed/Skipped, → NotVerified even when the recorded verdict was Satisfied (a replayed pass cannot outlive its data); evidence older than its freshness window → NotVerified (a stale Gap stays Failed); an unclassifiable NotApplicable → NotVerified; effectiveness is Unknown wherever `EffectivenessCapability` is `NotCollected` (186 of the 191 v2.0 rows; the six rows that read `DEV-*` results were NRG-only and left with v1.x) and read only from the evidence the row names otherwise (`DeviceControls`: ingested `DEV-*` results; `SignInLog`: the sign-in log, below); the manual `CIS-<number>` rows always resolve NotVerified. A v2.0 run compared with a v1.x run reports that the standard changed (`Get-TPBaselineRegressions`), never a regression, and the tenant comparison accepts `CIS-<number>` IDs; an exception on file for a control v2.0 no longer requires has no row to attach to and is unused (the view walks required rows only, and `New-TPBaselineException` refuses a control outside the baseline); review client exception files for such entries. The entry point resolves the view after license gating and the EDR declaration on both the live and `-FromResults` paths (`-BaselineTier`, or `BaselineTier` in `clients.json`, or the prior run's `TargetTier`, else Standard), records `BaselineVersion` / `TargetTier` in the metadata and writes `BaselineCompliance` and `BaselineRegressions` to the results JSON: that JSON is the integration contract, and the tool stays stateless (no ticket state, no SLA clocks). `Get-TPBaselineRegressions` compares against `-BaselineResults` only under the same baseline version and tier; otherwise it says the standard changed and compares only controls required in both runs at the same tier. The report section keeps configuration compliance and effectiveness visibility as two blocks and never says "compliant".

**Sign-in evidence is effectiveness, never a verdict (`Collectors/AAD/Invoke-TPCollectAADSignInEvidence.ps1`, `Lib/Get-TPSignInEffectiveness.ps1`).** The configuration controls say a block or an MFA requirement is in place; the sign-in log says whether it held. The collector (raw key `AAD-SignInEvidence`, no new scope: `AuditLog.Read.All`) reads the last 30 days through the beta `auditLogs/signIns` endpoint with server-side filters only: successful sign-ins whose `clientAppUsed` is one of the 13 legacy authentication clients Microsoft lists for the sign-in log filter, interactive AND non-interactive (Microsoft's own procedure checks both logs, and v1.0 returns interactive only), and successful interactive sign-ins whose `authenticationRequirement` is `singleFactorAuthentication` (not in v1.0). It keeps only id, time, user id and UPN, user type, app, resource, client app, error code and each authentication step's method, step requirement, success and result detail: no IP address, location or device. Each read publishes `SectionStatus` and a read that hit its page cap (5 pages of 1,000) is `Truncated`; a tenant without Entra ID P1 or P2 (Microsoft requires it to read sign-in logs through Graph) or an account without a reader role records `Available = $false` with `PremiumLicenseRequired` / `AccessDenied`. Five baseline rows name it as `EffectivenessEvidence` `{ Type = 'SignInLog'; Check; Scope }`: AAD-1.2 (`SingleFactorSuccess`/`AllUsers`), CIS-5.2.2.1 (`SingleFactorSuccess`/`PrivilegedRoles`, holders from `AAD-DirectoryRoles`, a role assigned to a group not resolved), CIS-5.2.2.3, EXO-1.6 and SPO-1.3 (`LegacyAuthSuccess`/`All`, `Exchange`, `SharePoint`, by resource id). **A single-factor record is not yet a bypass**: Microsoft documents that `authenticationRequirement` reads single-factor when an earlier MFA claim was accepted and says to check the authentication details too, so `Get-TPSignInMfaEvidence` counts a sign-in only when its recorded steps show no successful second factor or satisfied MFA requirement (Microsoft's listed methods and result details, or a multifactor step); one whose steps show MFA is named as not counted, and one with no recorded steps is never a bypass and never a pass (it leaves the row Unknown when nothing else is found). A page that fails after earlier pages keeps the events already read and fails the section; PIM eligibility not read (`SectionStatus.RoleEligibilitySchedules`) makes the privileged holder list incomplete, so a bypass found still counts and none found is Unknown. The judgment is asymmetric on purpose: one bypass in any read is `Ineffective` (named, up to five accounts), even from a truncated or partly failed read; `Effective` needs a complete read with none, and says the protection held for the sign-ins that happened, not that nothing could get through; anything else is `Unknown` with the reason. Approved emergency-access users (the `EmergencyAccess` record, by object id) are set aside and named; a group on the record is not resolved. It never touches `ObservedState`, and the evidence key is deliberately NOT in a row's `RawDataKeys`, so an unreadable log leaves configuration compliance as it was. Device-code sign-ins (`authenticationProtocol`) cannot be filtered server-side and are not read. The filters are documented but not yet run against a live tenant. `TP.SignInEvidence.Tests.ps1` drives the real collector against a stubbed Graph and pins each rule.

**Exception cmdlets (`Lib/Set-TPBaselineException.ps1`).** `New-`/`Get-`/`Set-`/`Remove-TPBaselineException` write `Config/baseline-exceptions/<tenant>.psd1` by the loader's own slug rule, as data-only PSD1 (`ConvertTo-TPBaselineExceptionPsd1`: single-quoted strings, quotes doubled, dates `yyyy-MM-dd`, `ExpiryDate` omitted when empty). **Coverage lines (`Get-TPBaselineCoverage`, in `Lib/Get-TPBaselineReason.ps1`).** Two metrics from the reason contract, never a score and never each other. Evidence: denominator = applicable required controls (`ReasonCode` `NotApplicable` excluded); Known = `Satisfied` + `ControlFailed` + `ThirdPartyHandled`; Unknown = every evidence-not-obtained code, listed by code as `Gaps`; `LicenseBlocked` in the denominator, reported separately; Known + Unknown + LicenseBlocked = Applicable. Effectiveness: denominator = required; Known only where `EffectivenessState` is `Effective`/`Ineffective`; `CapabilityCollected` says how many the tool can read today. Both blocks are top-level in `BaselineCompliance` (`EvidenceCoverage`, `EffectivenessCoverage`), on the console, and in both reports with the "not a score" sentence. The acceptance rules are tests: all-failed = 100% evidence coverage and 0 satisfied; all-satisfied with nothing reading effectiveness = 0% effectiveness coverage.

**Baseline plan (`Lib/Get-TPBaselinePlan.ps1`, `Get-TPBaselinePlan.ps1`).** A predictive VIEW that runs before the assessment: for the target tier it lists the required controls, the connections they need, and one `Expected` bucket per control in precedence order — `Manual`, `SkippedByOperator`, `ThirdPartyHandled`, `OptionalCollectorRequired` (from `Config/optional-collectors.json`, today only the SharePoint shell; a test derives the list from the evaluators that read `Get-TPSpoShellUnread`/`$noShell`), `LicenseBlockedExpected` (only from a license profile with `HasLicenseData`), `LicensingUnknown` (no profile: unknown until connection, never assumed held or blocked), else `Automatic`. `ExpectedNotVerified` = Manual + Skipped + OptionalCollectorRequired. It creates no finding and moves no score. The entry point computes it before connecting (licensing from `-BaselineResults` when given), writes `BaselinePlan`, and after the compliance view writes `BaselinePlanComparison` via `Compare-TPBaselinePlan`: unexpected NotVerified rows (a read that failed on the day) with their cause, expected-but-verified rows, and controls the plan never knew (a different tier or version, listed, not compared). `Get-TPWorkloadSkipMap` is the one copy of the `-Skip*` → raw-data-key table; a test pins it equal to the entry point's coverage table. **Tenant comparison (`Compare-TPTenantBaseline.ps1`, `Lib/Get-TPBaselineTenantComparison.ps1`, `Publishers/Publish-TPBaselineTenantComparison.ps1`).** Two DIFFERENT tenants against the NRG Security Baseline, offline, from two results JSON files (a prospect against an existing client). A VIEW like the baseline view itself: no findings, no score, no module state read or written, and it connects to nothing (`TP.TenantComparison.Tests.ps1` enforces that over the AST and tokens, and by mocking the network and sign-in commands to throw). It is NOT the run-over-run comparison: `Get-TPBaselineRegressions` and `Publish-TPDeltaReport` compare one tenant with itself and the delta report's different-tenant refusal is untouched (a test pins it). Owner decisions, final: INTERNAL only (the default output names both tenants; `-Anonymize` labels them A and B everywhere, file names included; no client-facing wording or branding is built) and ANY tier may be compared. Only controls required at BOTH tenants are compared (a Minimum run against a Standard run compares the Minimum controls); the rest are `NotCompared` with `Basis` `RequiredOnlyAtA`/`RequiredOnlyAtB` and the tier that required them. If the baseline versions differ the report says the standard changed and also leaves out (`DefinitionDiffers`) any control whose required tier or non-empty expected state differs between the files; a missing version is stated, never assumed equal. Equivalence must be established: the same version, or an identical expected state on both rows. A row with no expected state under a different or unknown version is NotComparable with cause `DefinitionNotEstablished`. **Classification keys on `ObservedState` AND `ReasonCode`, never on `BaselineStatus`** (which is a display status and would turn an approved exception into a state): BothSatisfied, BothFailed, DiffersASatisfied, DiffersBSatisfied, else NotComparable. A side carries a verdict only when it is Satisfied (code `Satisfied`) or Failed (code `ControlFailed`), no `LicenseBlocked` constraint, no `ThirdPartyHandled` code; a state that contradicts its own code is `Inconsistent`, an unrecognized state or code carries no verdict, and an absent code (an older file) is trusted only on Satisfied/Failed. NotVerified, NotApplicable, LicenseBlocked and ThirdPartyHandled on either side make the control NotComparable, listed with each side's code, and it is NEVER counted as a match: `Compared = Verified + NotComparable` and each side's required controls equal Compared + one-sided + DefinitionDiffers, both asserted. The headline is a count ("Same baseline posture on M of V controls that both tenants verified", which includes controls both fail), with the not-comparable and one-sided counts beside it; the model has no key named score, rank, percent or winner (a test walks it), and no output says "compliant". Both tenants' EvidenceCoverage and EffectivenessCoverage lines are shown (a block absent from an older file is stated as not recorded, never recomputed), with the sentence that coverage is not how well a tenant meets the baseline. Run dates beyond `-MaxRunGapDays` (default 7; the Weekly freshness class is 8) and the same tenant on both sides draw warnings; the latter still compares. An approved exception is a `Disposition` beside the observed state and is counted separately. **Privacy rules:** the model, Markdown, HTML and CSV carry control IDs (a strict `AAD-1.1`/`VM-VERIFY-01` shape: a permissive pattern would let a file smuggle a name through the ID), titles, states, reason codes (only codes in `Get-TPBaselineReasonCodes`; anything else renders `Unrecognized`), tiers, versions, dates and counts, and NEVER finding Detail, Reason, exception text, UPN, object name, `Operator`, `ExceptionsPath` or `TenantId` (not even in the default mode). With `-Anonymize` the identifiers of both tenants (domains, IDs, first labels as whole words) are replaced inside every rendered string, because a hostile or careless title could carry one; the scrubber orders by identifier length, not pattern length, or a first-label pattern would win and leave `.onmicrosoft.com` behind. Output is Markdown, a self-contained HTML page (no script, strict Content-Security-Policy, every string escaped) and a CSV whose formula-looking cells get a leading apostrophe. Every read of input data goes through `Get-TPObjectField`/`Get-TPNestedProperty`, enforced statically; licensing comes from the results file's own `SubscribedSkus` through `Get-TPTenantLicenseProfile -SubscribedSkus` and an unread profile reads "Not read", never "none". The batch runners sign in before they load the module, so they dot-source the writer's file and probe their root first. `TP.OutputFolderProbe.Tests.ps1` pins the probe, the message and the ordering in all five entry points. `TP.PythonIsolation.Tests.ps1` requires every other `& $py` call to be `--version` or the installer's `-I -m pip`, plants `openpyxl.py`/`json.py` in the output folder and the current directory and asserts the real library still loads. **A client-returned questionnaire PDF is untrusted (2026-10-13 scan):** both importers read it only through `Read-TPQuestionnaireFields` (`Lib/`, exported because the importers are scripts), which refuses a file above 32 MB, empty, a folder, or without a `%PDF-` header before Python starts; runs pypdf under a watchdog thread that ends the interpreter at 60 s (`os._exit(124)`, since `signal.alarm` does not exist on Windows); reads only the AcroForm field values, never page content; and refuses a pypdf below 4.0.0 with its version named (exit 3). Paths, limit and floor arrive as argv, never in the Python source. Memory is not bounded on Windows. The installer holds a present pypdf to the tested 6.20.1 but still does not install it. `TP.QuestionnairePdfBounds.Tests.ps1` pins each, including the watchdog with a sleep in place of the read and the floor with a stand-in `pypdf` module. **Advisory controls never claim compliance.** A control with no programmatic check must emit `NotApplicable`, never `Satisfied` or `Partial`. `Partial` is worth 0.5 toward the compliance score, so an advisory control scored as `Partial` hands every tenant free credit for a verdict the tool never computed. Enforced statically by `TP.EvaluatorHonesty.Tests.ps1`.

**US English spelling.** This tool produces deliverables for US clients, so all prose — findings text, remediation guidance, `Config/*.json` strings, comments and docs — uses US spelling: `license` not `licence`, and likewise `organization`, `behavior`, `defense`, `enrollment`, `catalog`, `analyze`, `normalize`, `authorized`, `sanitized`, `labeled`, `gray`. Note `Effort: 'License purchase'` in `Config/operational-impact.json` is pinned by `TP.ImprovementPlan.Tests.ps1` — the config value and the test's allowed set must change together.

**Variable names ignore case.** `$P` and `$p` are one variable. The HTML publisher set its brand colors in `$P`, `$S` and `$A`; two loops lower in the same function iterate `$p` and `$a`, so the stylesheet printed `System.Collections.Specialized.OrderedDictionary` where the primary color belonged and the report header lost its background on the first live run under the NRG profile. **StrictMode.** `Set-StrictMode -Version Latest` is active module-wide. Referencing a property an object does not have THROWS before a `??` default can apply, so fields read off external cmdlet output whose shape is not guaranteed must go through `Get-TPObjectField`, not direct dot-access.

**The test suite is judged by `tools/Invoke-TPTestGate.ps1`, never by `FailedCount`.** A container that fails DISCOVERY runs no tests, so it reports no failures: a merge resolution dropped one closing brace in `TP.IdentityTruth.Tests.ps1`, the local check read `FailedCount`, saw 0, and approved the merge; Pester on main then failed at parse before a test ran (CI runs 554 and 556, 2026-10-15). A run that pointed at a path with no test files passes the same check. The gate AST-parses every test file in `Testing/` and `Email-IR/Testing/` first and reports the file and line, then accepts the run only when Pester returned a result that says `Passed`, at least one test ran, and no failed test, block or container is reported — reading each field through `PSObject.Properties` so a shape this Pester version does not emit is "not reported", never a zero. Both CI Pester jobs and the pull-request checklist call it, and `TP.TestGate.Tests.ps1` drives it with the failed-container and zero-test shapes and fails if a workflow calls `Invoke-Pester` directly.

**Security rules have no allowance, and CI modules are installed by hash.** `tools/Invoke-TPSecurityAnalysis.ps1` (the "PowerShell Security Analysis" job; rules in `PSScriptAnalyzerSecurity.psd1`) runs PSScriptAnalyzer's security rules at every severity with `-IncludeSuppressed`, so an in-source `[SuppressMessage()]` fails like the finding it hides; fix the code instead. CI installs PowerShell modules only through `tools/Install-TPPinnedModule.ps1`, which takes the exact version and the gallery package's SHA-256 from `tools/pinned-modules.psd1`, refuses a mismatch before reading the package, and refuses an entry outside the module folder; each job then imports the pinned version with `-RequiredVersion`. A bump edits the version and its hash together; `tools/Test-TPPinnedModuleFreshness.ps1` (weekly in `oss-scanner-image.yml`) fails when a pin has a newer release in its own major version public for seven days, and only warns about a new major version, which is a migration to plan, not a pin to bump. The suite runs under Pester 6; the gate keeps a Pester already loaded and refuses one that is not the pin, because Pester 6 loads a compiled assembly that a second import into the same session cannot replace. `TP.SecurityAnalysis.Tests.ps1` fails a workflow that calls `Install-Module`/`Install-PSResource`/`Save-Module`. **Two scans look at the tool running, not at its code (`TP.RuntimeScans.Tests.ps1`).** `.github/workflows/dast.yml` starts the real `Lib/Start-TPWebServer.ps1` on loopback over `tools/New-TPWebScanFixture.ps1` (data only, no network) and runs OWASP ZAP's baseline scan with the AJAX spider against it, with `-z "-silent"` so the rules are the pinned image's own (without it zap-baseline downloads rule add-ons at start, and the first CI run judged with three rules the same image never raised offline); every rule not reviewed in `.zap/rules.tsv` is a WARN and any WARN or FAIL fails the job, a reviewed exception carries its reason on the same line, and `-I` (pass on warnings) is forbidden. It is passive: no attack payload is sent, so it scans what the server says, not what it does under attack (`docs/security/TESTING-METHODOLOGY.md` maps every scan to its PTES phase and says which phases nothing automates). `oss-scanner-image.yml` scans the built image with Trivy (HIGH/CRITICAL, `--ignore-unfixed` because nothing here can act on a CVE the distribution has not fixed, SARIF to Code Scanning) and checks `.oss-scanner/Dockerfile` at every severity; a finding passes only when reviewed into `.trivyignore.yaml` with a statement, and its first run made the image drop root (DS-0002). Both scanners run from images pinned by tag and digest in one-line Dockerfiles under `.github/scanners/` that Dependabot's docker ecosystem tracks (a digest in a workflow step is never updated); the job reads the FROM line and runs exactly that. A digest nothing tracks rots in days: the base-image digest pinned on 2026-10-19 was gone from MCR (404) by 2026-10-24 because the tag was re-pushed, and only Dependabot's docker tracking had moved `main` past it; a digest in a workflow step has no such keeper, which is why the scanner pins live in Dockerfiles. **InjectionHunter runs in the same gate and its findings are reviewed, not suppressed.** A new finding fails until the code is fixed or the finding is added to `tools/injection-baseline.json` with a reason a reviewer can check (path, rule, the flagged line's text with whitespace collapsed, a count); an entry nothing matches fails as stale, so remove it when the code goes. The one automatic pass is an UnsafeEscaping finding whose every `-replace` replaces with the constant empty string (`Test-TPRemovalOnlyReplace`, read from the AST at the finding's offsets). Prefer an instance read with a literal name, or splatting and `&` for dynamic commands, over adding an entry; a value quoted into a filter or generated script is refused when it holds U+2018..U+201B, never escaped.

## Batch Mode

`Config/clients.json` requires the following fields for every client: `ClientName`, `TenantDomain`, `TenantId` (GUID), `DelegatedOrg` (the `.onmicrosoft.com` routing domain — not the primary domain), `DnsDomains` (array), `SkipPurview`, `SkipTeams`, `SkipSharePoint`, `SkipIntune`, `SkipPowerPlatform`, `SkipDNS` (all boolean), `Notes`, and `Active`; `ThirdPartyEDR` is optional. `BaselineTier` and a `Collectors` block (opt-in collectors keyed by the optional-collector catalog id, today `SharePointShell`; read by `Get-TPClientCollectorFlags` in the entry point, the batch runner and the standalone plan) are optional too. A collector flag is an operator expectation that turns the collector on, never proof it worked: a failed read still reports as not verified and the plan comparison names it. The batch runner passes each client's `-TenantDomain` and `-KeepSession` to the assessment, so tenant pinning and the Purview `-DelegatedOrganization` apply per client. **One clients file serves the whole batch.** The runner passes the file it was given to every assessment as `-ClientsFile` (an assessment reads its client's record, by `-TenantDomain`, only through `Get-TPClientRecord`, never from a second hard-coded path: a batch run from a file kept elsewhere used to lose each client's declared EDR and awareness product, monitoring addresses, baseline tier, collectors and routing domain, which reads as a client with more gaps), a named file that is missing or not valid JSON is fatal (exit 4) before anything connects, and a record may carry `Profile` (validated by `Resolve-TPProfilePath`; without it the run uses `TP_PROFILE`) so clients of different practices share a batch. `Profile`, `ThirdPartyEDR` and `ThirdPartyAwareness` are judged before the first sign-in (`Get-TPProductNamePattern`, the one product-name rule; `Set-TPThirdPartyEdr` and `Set-TPThirdPartyAwareness` carry the same character class in a parameter attribute, pinned equal) and `-WhatIf` prints what each record sets. A record cannot switch off a profile's declared EDR, so keep a declaration in the profile only when every client of that practice has it. The shipped `Config/clients.json` is a tracked sample: a working copy holds client data and must not be committed.

`DelegatedOrg` must be the `.onmicrosoft.com` routing domain. Get it from Microsoft 365 Admin Center under Settings then Domains for each client. Get `TenantId` from `https://login.microsoftonline.com/domain/.well-known/openid-configuration` — the GUID in the issuer field is the TenantId.

Test sequence before first full run: run with `-WhatIf` first, then `-OnlyClient nrgtechservices.com -JsonOnly`, then full batch.

## Common Tasks

**To add a new control:** add the entry to `Config/controls.json` with all required fields including `LicenseRequirement`, add the evaluator function to the appropriate file in `Evaluators/`, verify the function name matches `EvaluatorFunction`, verify the collector sets the data key referenced by `CollectorDependency`, and add the new function name to both `FunctionsToExport` in `TenantPosture.psd1` and `$script:ExportedFunctions` in `TenantPosture.psm1`.

**To add a new client:** get the `TenantId` from the OpenID configuration endpoint, confirm the `.onmicrosoft.com` routing domain from M365 Admin Center, add the entry to `clients.json`, and set Skip flags based on the client's license tier — set `SkipPurview` and `SkipPowerPlatform` for Business Standard clients.

**To debug a collector:** run `-JsonOnly`, open the output JSON, find the collector key under `RawData`, check the `Success` field and `CollectedAt` timestamp, and check the `Exceptions` array for registered errors.

**To debug a wrong evaluator result:** confirm what raw data key it reads, verify the collector set `Success` to `true`, and inspect the specific fields the evaluator accesses against the actual collected data. Evaluators must never crash on missing fields — use null-conditional operators or explicit null checks throughout.

## Security Requirements

The tool is **read-only without exception**. No evaluator, collector, or publisher may write to tenant configuration. All Graph calls use GET only. All EXO calls use read-only cmdlets only. Any future write capability belongs exclusively in `Apply-TPBaseline.ps1` with mandatory `WhatIf` support. Raw data is stored in module-scope memory only and never written to disk unencrypted. JSON output must not include credentials, tokens, or user PII beyond UPN and display name. The incident-response mode is the documented exception (SECURITY.md, "Data the Tool Writes"): its JSON carries sign-in addresses, geolocation and message metadata because they are the indicators; a phone number is masked to its country code and last two digits (`ConvertTo-TPMaskedPhone`) and a URL's credential-bearing query values and userinfo are redacted (`ConvertTo-TPRedactedUrl`, `Email-IR/Lib/`) at collection, never at render, and `TP.IRDataContract.Tests.ps1` drives the real collectors to prove the raw values never reach the raw data.
